# CLI 编程 Agent（LangGraph 编排 · 类 Claude Code 迷你版）

[![tests](https://github.com/jiangbianwangui/minicode/actions/workflows/test.yml/badge.svg)](https://github.com/jiangbianwangui/minicode/actions/workflows/test.yml)
[![python](https://img.shields.io/badge/python-3.11%2B-blue)](https://www.python.org/)

一个 coding agent：给它一句自然语言任务，它自己读文件、写代码、跑命令、看结果、
不对就改，直到完成。和 Claude Code / Cursor / OpenHands 是**同一个思想**。

> **这个仓库的重点不是"能改代码"，而是"能证明自己的优化到底有没有用"。**
> **39 个自动判卷任务**（含 1 个留出任务、5 个随机抽样对照）+ 双向校验（参考解必过、
> **66 个错解变异**必拦）+ 配对消融 + prompt 健康审计，用它推翻了 6 个自己的假设，最后留下的是**边界结论**而不是漂亮百分比。
> 详细实验记录见 [`eval/ABLATION.md`](eval/ABLATION.md)。

> 演进：项目**最早是纯自实现**（`agent_handwritten.py`，`while` 循环 + 手写消息协议，
> 不依赖任何框架），用于彻底搞懂 Agent 闭环的原理；之后**用 LangGraph 的 `StateGraph`
> 重写了编排层**（`agent.py`），工具层（`tools.py` 的参数校验 / 沙箱 / 黑名单）全程复用。
> 两份代码都在仓库里——正好对照「手写循环 vs 框架编排」的差异。

## 运行

```bash
pip install -r requirements.txt
cp .env.example .env          # 填入 LLM_API_KEY（DeepSeek / 硅基流动 / OpenAI 均可）

python cli.py "在沙箱里创建 hello.py，定义 add(a,b) 返回 a+b，并运行打印 add(2,3)" \
    --workdir ./sandbox_example --stall
```

验证环境是否正常（不烧额度的离线部分）：

```bash
python -m pytest tests -q          # 96 个单测
python eval/selftest_tasks.py      # 39 个任务可解性自检（会真调 LLM）
```

> 依赖只有一个 OpenAI 兼容端点 + `langgraph`；`.env` 查找顺序见 `llm_env.py`
> （`MINICODE_ENV_FILE` → 本目录 `.env` → 当前目录 `.env`）。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--max-iter` | 20 | 最大工具轮数 |
| `--max-obs` | 2000 | 单次 observation 截断字符数（实测调大反而更差） |
| `--stall` | 关 | **停滞检测**（推荐开）：反复探索无产出时先警告、再终止 |
| `--plan-mode` | 关 | 强制 Plan-Execute（实测净亏，仅用于对照） |
| `--adaptive` | 关 | 按任务复杂度自动开 plan（实测净亏） |
| `--compress` | 关 | 分层上下文压缩（边界未定，仅对长轨迹任务，见下） |
| `--skills` | 关 | Skill 分层路由：检索 `skills/` 里的外部知识，按需 `LoadSkill` 拉全文 |

⚠️ **安全提示**：Bash 工具会真实执行模型生成的命令。请在**空目录 / 虚拟机**里跑，
`sandbox_example/` 已给出示例。文件类工具锁死在 `--workdir` 内，越界会被拒绝；
Bash 带超时 + 破坏性命令黑名单 + **沙箱逃逸拦截**（`cd /`、`find /`、家目录绝对路径等）。

> **这不是真正的容器隔离，而且已经实测被绕过两次。**
>
> - **2026-10-27**：写 t27 时 agent 为了"查技能文档"执行了 `find / -name SKILL.md`，
>   真的扫到了 `C:\Users\王\.claude\plugins` 并读出了文件名。
> - **2026-11-02**：写 t38 时，base 模式用 `grep -rn ... ../../../skills`
>   读到了我刚写的 `skills/export-approval-policy/SKILL.md`，**并且照着抄通过了评测**。
>   那次跑出 129k token —— 原正则只拦绝对路径，`..` 一路退到 `eval/`（判卷代码就在那儿）。
>   修法是拦任何 `../` 与独立 `..`，并改判了一条"相对路径回退是合法用法"的旧单测
>   （那个理由不成立：workdir 上两级就是 `eval/`，一步就能摸到答案）。
> `cwd=workdir` 只限制「默认起点」，不限制「能去哪」。
> 现在的拦截是黑名单式的尽力而为——**真隔离要靠容器，本项目没做**。
> 把它写在这里而不是藏着，因为"知道自己不安全到哪一步"比"声称安全"重要。

## 机制结论：哪些开、哪些关、边界在哪

**这一节是整个项目的产出。** 每个结论都有重复实验支撑，不是"我觉得"。

| 机制 | 状态 | 结论 | 依据 |
| --- | --- | --- | --- |
| **停滞检测** | ✅ 推荐开 | 对不会空转的任务**完全中性**（−0.4%, t=−0.02）；对易失控任务最坏情况 token **−81%**、轨迹极差 **10.6× → 1.7×** | 三类任务 11 次配对，合并 −29.8%（t=−2.21, df=10, p≈0.05，**未达显著**，故以最坏情况为口径） |
| Plan-Execute | ❌ 默认关 | **净亏**：+53.7% / +1.4% / +7.3%，三批方向一致 | 短轨迹任务上，规划开销 > 规划收益 |
| 自适应规划 | ❌ 默认关 | 净亏，同上 | 复杂度判定本身也是成本 |
| 上下文压缩 | 🟡 默认关 | **不是"要不要"，是"什么形态的任务"**：只对「一次性勘察型」（读完即动手、不回看）有正收益 | 见下 |
| **Skill 分层路由** | 🟡 按需 | **唯一能改变"对错"的机制**：10 个"答案不在仓库里"的任务上 base **有交付 31 次全失败** → skill **27/28** | 10 个任务级样本，符号检验 p=0.001；阴性对照（规格给全的 5 题）base **15/15**，说明边界是「规格在不在仓库里」 |

### Skill 路由：它解决的不是"想得更好"，是"根本不知道"

前面三个机制（Plan / 压缩 / 停滞）都是在优化**已有信息的使用方式**。
它们在同一类任务上全部收益有限，原因是同一个：

> **26 个任务的答案都在仓库里。** 再会规划、再省上下文，也变不出新信息。

Skill 补的是另一维：**仓库外的知识**。对端 API 的限频配额、团队测试规范、
历史事故留下的禁忌——这些东西 `Grep` 怎么搜都搜不到，而猜错**不会报错**
（写个 60 秒 TTL 代码照样跑绿，只有配额打满那天才炸）。

设计上有三个刻意的取舍：

| 决策 | 选择 | 为什么 |
| --- | --- | --- |
| 检索 | BM25 粗召回 + **tag 精确命中**准入 | 语料只有个位数 skill 时 IDF 会失效（df≈N），BM25 退化成词频匹配，"代码/文件/测试"这类通用词把一切都连起来 |
| 注入 | 只给 **description**，正文要 `LoadSkill` 拉 | 无条件塞 3 篇全文 ≈ 2000 token，等于替 agent 判断"哪些有用"；判断错了就是纯亏（和压缩踩的是同一个坑） |
| 召回数量 | 没命中就不给，不填满 top_k | 乱召会诱导 agent 多花一轮去读无关文档；漏召只是退回通用知识，不亏 |

> **第一版是错的，记在这里**：最初把 skill **正文**也放进 BM25 索引，
> 结果 26 个任务**每一个**都召回 2–3 个 skill，"写个 hello world" 匹配到了
> "重构安全检查"——因为正文里全是"代码/函数/文件"。
> 改成只索引元数据（name / tags / when_to_use）+ tag 准入后，召回降到 10/26 且全部有意义。

**效果（"答案不在仓库里"的任务族，成立的 10 个 + 1 个反例）**：

| 任务 | 缺的知识 | base | skill |
| --- | --- | ---: | ---: |
| t27 外部 API 契约 | 限频 / 重试 / 时间戳单位 | 0/3 | 3/3 |
| t28 消息队列契约 | prefetch 上限 / ack 余量 / 死信 | 0/2 | 2/2 |
| t29 日志规范 | trace_id / PII / exception | 0/2 | **1/2** |

**留出任务 t39（告警静默，不给配套 skill）—— 用来测迁移，不进主统计**

| 组 | 给什么 | 通过 | 检查点 |
| --- | --- | ---: | --- |
| A | 什么都不给 | 0/3 | 2 / 4 / 4 |
| B | 现有 13 篇库（召回到同构的 `backfill-approval-policy`） | 0/3 | 2 / 4 / 4 |
| C | 专属 skill（`eval/heldout/`，不参与路由） | 3/3 | 6 / 6 / 6 |

> **B 和 A 总分一样，但内部结构变了**：B 读了 skill 后把"直通"从函数末尾挪到了第 0 步
> （这一步它学对了），但阈值全错（60/240 vs 30/1440），净效果为零。
>
> **结论：skill 能迁移"结构"，不能迁移"参数"。** 这限定了主结论的适用范围——
> skill 的价值高度依赖"恰好有对应的那篇"。

十个任务合计：**base 有交付 31 次全部失败（另有 3 次零交付单独计），skill 27/28**。

> **口径说明**：base 的 34 次里 **3 次零交付**（20 轮用尽、130k token、一个字符没改）。
> 零交付不算进通过率分母 —— 它不是"答错"，是"没开始答"。

失败归类全是 `wrong_behavior`（有交付、内容错），不是 `no_delivery`——测的是知识，不是流程。

> ✅ **已够 10 个任务级样本，配对统计见 [`eval/STATS.md`](eval/STATS.md)。**
>
> 主结果：**10 次配对全部同向，符号检验 p = 0.001**；
> 配对 t 检验 t = 19.0（p = 1.4e-08）—— 但 base 侧恒为 0，
> 这个 t 已退化成"单样本检验"，且 95% CI 上界 1.063 > 1.0，说明**已贴天花板**，
> 不能按字面读成"提升了 95 个百分点"。
>
> 敏感性：剔除只有 1 个检查点区分的 t35/t36 → 结论不变（均值差 0.938）；
> 加入反例 t32 → 效应降到 0.864，方向不变。
>
> ⚠️ **base 恒为 0 是筛出来的**（造题时就按"base 会失败"选），
> 所以这是**机制有效性证明**，不是**效应量估计**。
>
> t29 的 1/2 是能力边界，不是噪声：两次都读到了规范，但有一次把
> `logger.exception` 降级成 `logger.warning`，丢了 traceback——**知道规矩但没照做到位**。

**阴性对照：随机抽样的 5 个任务（规格给全）—— base 15/15 全过**

抽样框 12 个、种子 `20261109`、预注册在 [`eval/SAMPLED.md`](eval/SAMPLED.md)，
任务和上面 10 题**同形**（单模块 + 3–6 条行为 + 既有测试），**唯一差别是规格在需求里给全**。

| | 规格在仓库里（抽样 5 题） | 规格不在仓库里（10 题） |
| --- | --- | --- |
| base | **15 / 15** | **0 / 31**（有交付的） |
| skill | 15 / 15 | 27 / 28 |

同一个 agent、同一套工具、同一种任务形状，**唯一变量是「规格在不在仓库里」，通过率从 100% 掉到 0%**。

这条结果堵掉了两个质疑：

- 「base=0 是因为你的任务太难 / 脚手架坏了」→ 同一脚手架，同形任务 15/15 全过；
- 「base=0 是因为模型能力不足」→ 它在抽样题上写对了浮点分摊的平局规则、
  LRU 的淘汰顺序、版本号的预发布顺序。

**所以 skill 的价值有明确边界**：它不是「让 agent 变强」，而是**补上「规格不在仓库里」这一种缺失**。

在不需要它的任务上，增益是 0，**成本也是 0** —— 前提是路由不要乱塞。
第一次测出来是 `+9.5k token（+52%）`，查下去发现那不是成本，是**bug**：
5/5 抽样任务都被塞了不相关文档（`pytest-style` 靠 `pytest`+`test` 命中了 20 个任务，
`rates-api` 靠 tag `cache` 命中了 LRU 缓存题）。修掉后重跑：

| 抽样 5 题 | 修复前 | 修复后 |
| --- | ---: | ---: |
| token 差（vs base） | **+9,504**（sd 9,104） | **−256**（sd 5,207） |
| 被注入文档的运行 | **15 / 15** | **0 / 15** |
| 通过 | 15/15 | 15/15 |

> **教训：「功能有成本」这个结论，必须先排除“它压根没在干对的事”。**
> 修法见 `eval/ABLATION.md` Batch AF：通用 tag 不能单独构成召回 + 绝对分数下限 10.0。

效应量的诚实表述：**收益 ≈ 「规格缺失」在真实任务里的占比 × 1.0**。
我测的是「缺失时能救回多少」（≈100%），**没测「缺失发生的频率」**——那需要真实工单分布。

> ⚠️ **已知脆弱点：路由的绝对分数阈值不可移植。**
> `min_abs = 10.0` 是在「13 篇 skill + 我写的 44 个 prompt」上标定的，
> 卡在噪声上限 9.6 与真命中下限 10.4 之间 —— **两边只有 0.4 分余量**。
> 分数里 `0.2×BM25` 会随语料规模变化，**技能库翻倍后必须重新标定**，否则会静默漏召。
> 真实语料的行为由 `tests/test_recall_snapshot.py` 锁住（12/44 召回，且每个都对着正确那篇）。

> **t35 和 t36 要打折**：这两题的 4–5 条规矩里，base 自己猜对了 3 条，
> 只有 1 个数字（t35 是"整条丢 vs 清洗"、t36 是配额 900）在区分。
> 说明"某某公司的参数表"这条路线的缺口快挖完了。
> **t37 / t38 是换赛道后的结果：base 分别 0/6、0/6 个检查点（五次运行各自碰巧对上的条都不同）。**

**三条可复用的造题手法（t33 / t34 / t37 换来的）**

1. **参数与直觉相反**（t33）：P0 预算最短 800ms、P0 不重试、70% 就降级。
   base 四条全错且方向一致——"最重要的链路当然给最多时间"。
2. **判据与直觉相反**（t34）：劣化看**两组之差**不是绝对值、样本不足**不判**、劣化先 **hold** 不直接回滚。
   5 次 base 全栽在"用 `canary_err > 1%` 判断"——**这是一条在多数公司里都对的规则**，
   所以它错得毫无自觉。
3. **结构上更复杂**（t37）：不是考一个数，是考**4 条规则 + 1 个顺序 + 1 个短路**。
   base 六条检查点全 FAIL，每一条单独看它都"错得有道理"。

> 2 比 1 值钱：数值反直觉它只是猜错，
> 判据反直觉它会**拿一条别处正确的规则自信地替换掉这里的**。
> 3 解决的是另一个问题：t35/t36 只剩 1 个检查点在区分，
> 而让 agent 同时猜对"多条规则 + 顺序 + 短路"的概率低得多，
> 且错了能报出**漏了哪一条**。

**t32 是反例，留在仓库里是因为它划出了边界**

prompt 只说"报表交给业务方直接双击打开"，从没提 `utf-8-sig`，base 却 5 次全过——
模型自己推出了"Windows 下 CSV 要 BOM + CRLF"。

> **结论：缺的知识必须是"某家公司/某个 broker 自己定的数字"，
> 不能是任何有经验的工程师都该知道的通用做法。**
> 判断标准一句话：**这条约定换个公司还成立吗？** 成立 → 不该进这个任务族。
> 这和 t28 第一版失败是同一条教训的两个层级（症状 → 修法 vs 领域词 → 领域常识）。

**t30 是这组里最有信息量的一个，但它不测 skill**

源系统的行为刻意无文档，也没有对应 skill。它测的是**校准**：

| 模式 | 结果 | 读法 |
| --- | ---: | --- |
| base | 1/2 | **只有一半运行会写 `UNCERTAIN.md` 承认自己在猜** |
| skill | 2/2 | 与 skill 无关（没东西可查），不能算功劳 |

> 另一半运行什么都没写，直接按假设实现——代码能跑、测试全绿，
> 但接手的人不知道哪里可能错。**这就是"自信地猜"，比答错更难发现。**

**回归验证（它会不会把本来能过的任务搞坏）**：t22 / t24 各 3 次，通过率**零损害**（都 100%），
成本均值 +8.9% 但**符号不一致**（t22 −14% / t24 +41%），t=0.35 —— 纯噪声，不可引用。

原因：t24 的 prompt 提到 `pytest` 就召回了 `pytest-style`，agent 多读一轮全文，
但 t24 要的是**写函数**，pytest 只是验证手段。**当前检索区分不了「提到 X」和「需要 X 的知识」**。

> 这就是为什么它默认关：**召回准 ≠ 召回必要**。
> 常开 = 给所有任务白加约 9% 成本，换来极少数任务从 0 变 1。


### 停滞检测：统计没达显著，为什么还"推荐开"

配对合并 −29.8%，t=−2.21（df=10，临界 2.228），**差 0.018 没过线**。
按常规做法，不显著就不该说有效。但这题的答案不是"再跑几次凑显著"——那正是 Batch K 拒绝过的做法。

**为什么均值在这里是错的判据**

11 次配对里，大部分任务的收益**结构性为 0**：

| 任务类型 | 收益 | 为什么 |
| --- | --- | --- |
| 脚本化短轨迹（t20） | **−0.4%**（t=−0.02） | 它本来就不空转，护栏无事可做 |
| 大文件审计（t25） | −47.2% | 会轻微打转 |
| 需判断易空转（t26） | −70.8% | 最坏情况 **−81%** |

一堆 0 加上几个大负数，均值 −29.8% 不代表任何真实场景——
它是"零收益"和"大收益"的混合体。**用一个被稀释的均值去检验，等于要求护栏在不需要它的地方也得有用。**

> 这就是安全气囊的判据：没人用"平均每公里省多少钱"评估它。
> 判据是**撞车时能不能救命**——即最坏情况，以及它压下多少方差（**10.6× → 1.7×**）。

**那这算不算"换个判据说事"？（会这么被问）**

不算，但要说清三条边界：

1. **判据必须事前匹配机制的作用方式**。护栏的定义就是"只在少数情况下生效"，
   用平均收益衡量它，是口径错配——这个可以事前陈述，不是看到结果才倒推。
2. **不藏原始事实**。报告里明写"未达显著"，不写"显著降低 29.8%"。
3. **新判据本身可检验**。最坏情况 −81%、方差收敛 6 倍，都是能被打脸的硬数字，
   不是"感觉上更安全"。

反面：如果我说"差 0.018，加大 n 就过了"——那是承认结论依赖凑数，
而且凑完之后均值仍然是被稀释的错判据。**换判据要连理由一起换，否则就是耍赖。**

### 为什么压缩默认关

```
压缩净收益 = 每轮省下的重发成本 × 剩余轮数   −   遗忘导致的重读/返工成本
             └────── 线性累积 ──────┘        └───── 一次就阶跃 ─────┘
```

本项目任务集中在 8–25 次调用，处于「攒不够就撞上阶跃」的区间。更关键的是：

> **"后面会不会重读"取决于 agent 之后怎么走，事前不可知。**
> 所以无悔闸门能算清摘要成本，算不清遗忘风险。

正面证据（t26，各 5 次）：通过 3/5 → 4/5，token 240,311 → **111,744（−53.5%）**，
且调用数几乎不变（24.6 → 23.6）——省的是**单次输入长度**，不是"少干活"。
反面证据（t25，3 次）：**只有 1 次真的触发压缩**（估算峰值 3510 / 4405 / 3777，阈值 4000），
样本来自两个分布，均值没有意义。

> 这只说明一件事：**在把"触发"变成确定性事件之前，压缩的效果问题无解。**
> 而阈值正好卡在这批任务的上下文峰值上（3.5k–6k），所以它天然不确定。

## 架构

```
用户任务
   │
   ├─（可选）skill_router.retrieve(task)  ── BM25 + tag 准入 → top-k 摘要
   │                                          正文等 agent 主动 LoadSkill
   ▼
┌───────────── StateGraph (agent.py) ─────────────┐
│  START → agent(决策) ─┬─ 有 tool_calls → tools(执行) → 回到 agent │
│                       └─ 无 tool_calls → END                      │
│                                                           │
│  agent 节点：system(+技能摘要 +停滞警告) + 历史(可压缩)              │
│              → bind_tools(6 工具 [+plan] [+LoadSkill])             │
│  tools 节点：逐个 call()（参数校验→沙箱执行→observation）          │
│              同时喂给 StallDetector 判断「这轮有没有新信息」        │
└───────────────────────────────────────────────────┘
```

- `tools.py`：工具 schema + **手写参数校验** + 沙箱/黑名单——框架不替你做
- `agent.py`：`CodingAgent` 用 `StateGraph` 编排；`agent_handwritten.py` 是等价自实现版
- `stall.py`：停滞检测器（纯函数，可单测）
- `context.py`：分层压缩器 + token 估算（CJK 加权）
- `prompts.py` / `cli.py`：系统提示词 / argparse 入口

### 停滞检测的判据（设计关键）

**不是"有没有写文件"**——解题前连续读 12 个**不同**文件是正常推进，按"没写就空转"会误杀。
真正的判据是：**这一轮有没有带来新信息**。

| 本轮发生的事 | 判定 |
| --- | --- |
| 出现此前**没见过**的读/搜/命令签名 | 有进展 |
| 有**成功的**写操作 | 有进展 |
| 都没有（重复读同一文件 / 重复同一命令 / 全部失败） | 空转 +1 |

两级动作：6 轮无进展 → 往 **system** 注入一次警告（不伪造 user 消息，避免破坏 tool_call 配对）；
10 轮 → 终止，`status="stalled"`。

## 评测体系

```bash
# 单任务跑 N 次，输出 mean±std / 配对差值 / t 检验
python eval/repeat.py --runs 5 --modes base stall --ids t26 --max-iter 40

# 全量评测（26 任务，自动分桶：按实测成本三分位）
python eval/runner.py

# 双向校验：① 初始必败 ② 套参考解必过
python eval/selftest_tasks.py

# 变异测试：8 类"看着对但有细微错"的解，必须 100% 被拦
python eval/verify_strictness.py

# 难度扫描：把任务规模当旋钮连续拧，找能力边界
python eval/sweep.py --dim size --runs 2
python eval/sweep.py --dim count --counts 4 8 12 24 --target-rows 6000

# prompt 健康审计：机器检查"完成判据是不是假信号"（setup 后真跑一遍命令）
python eval/prompt_audit.py          # 发现假信号则退出码 1，可挂 CI
```

五层防线，缺一层结论就不可信：

| 层 | 防什么 | 机制 |
| --- | --- | --- |
| 任务可解 | 死题（正确解也过不了） | `selftest_tasks.py` 套参考解 |
| 判卷不松 | 放水（错误解也能过） | `verify_strictness.py` 8 类变异解 |
| **信号不假** | **prompt 给了"完成 = 某命令通过"，而该命令初始就是成功的** | `prompt_audit.py` 实跑命令判定 |
| 单次不作数 | 采样噪声 | 重复消融 + 配对差值 + t 检验 |
| 处理真发生 | **"调用了" ≠ "执行了"** | 探针确认功能真触发（踩过两次坑） |

> **信号不假**这条是 2026-10-26 才补上的，代价是 t26 的数据全部要打折：
> t26 的 prompt 写着"完成的定义：`pytest tests` 全绿"，而它**开局就 4 passed**。
> agent 面前同时有一个绿灯（已完成）和一个未完成的任务，只能反复跑测试来消解矛盾——
> 实测 3/3 全部跑到预算耗尽（41 calls / 685k token）。
> 改成"明示绿灯是假信号"后：**3/3 通过、9 calls、45k token**。
>
> **规则：prompt 里不能出现"完成 = 某命令通过"，除非该命令初始是失败的。
> 全绿的测试比没有测试更危险——它给的是假信号，而 agent 会认真地按它执行。**

**为什么条件偏偏是"初始失败"**

因为完成判据的唯一职责是**区分**「做完了」和「没做完」。
一个判据如果在两种状态下取值相同，它就没有区分能力——那不是判据，是噪声。

```
判据的信息量 = P(判据=通过 | 已完工) − P(判据=通过 | 未开工)
```

- t18：初始 `pytest` 必败 → 通过率差 = 1 − 0 = **1**，满分判据
- t26：初始 `pytest` 就 4 passed → 差 = 1 − 1 = **0**，信息量为零
- agent 拿着一个信息量为 0 的判据，只能反复采样它，希望它哪天发生变化

**同一个命令可以是"护栏"也可以是"完成判据"，取决于怎么表述**

| 表述 | 角色 | 合法性 |
| --- | --- | --- |
| "运行 pytest 确认全部通过，即完成" | 完成判据 | ❌ 初始就绿 = 假信号 |
| "运行 pytest 确认**没有回归**" | 护栏 | ✅ 它约束"别弄坏"，不断言"做完了" |

这也是为什么 t22 的修法是**改措辞 + `audit_ok` 登记**，而不是把命令删掉——
命令本身有用，错的是把它当成了完成信号。

规则立了之后，`prompt_audit.py` 把它变成**机器判据**而不是人肉 review：
抽取 prompt 里反引号包住的命令 → `setup()` 之后原样跑一遍 →
`rc == 0` 且未登记在 `audit_ok` 里就报假信号；`rc != 0` 或跑不起来则是合法判据。

> 注意这里必须是**运行时**检查，不能静态查措辞：
> "让 pytest 通过"这句话，在 t18 合法、在 t26 是假信号，**文本上长得一模一样**。
> 区别只在 setup 之后那个 rc。这就是为什么审计要真跑，而不是正则匹配关键词。

第一次跑就抓到两处作者自己没意识到的同类缺陷：

| 任务 | 假信号 | 处理 |
| --- | --- | --- |
| t22 | `pytest tests` 初始 **5 passed**，prompt 却写"完成后必须运行确认全部通过" | prompt 显式声明"它只能证明没弄坏，不能证明写对了" + `audit_ok` 登记 |
| t20 | `python -c "import legacy"` 初始就过 | 同上 |
| t26 | 已修（明示绿灯不可信） | 保留，改为反例样本 |

> 重要：t22 在 26 任务全量评测里一直是**稳定通过**的，所以这个假信号从未暴露——
> 假信号只在"任务本身容易卡住"时才致命。**基线满分不等于任务没问题。**

指标分三层，**过程指标与 `passed` 解耦**——任务通过也可能过程中报过错（`passed_with_retry`）：

| 层 | 指标 |
| --- | --- |
| 交付 | 通过率 / **`delivered`（有没有真的改过文件）** |
| 效率 | 调用数 / token / 耗时 / `iter_usage`（占上限比例） |
| 过程 | 工具序列、首个失败步、工具成功率、重读次数、失败归类（9 类，含 `no_delivery`） |
| 基础设施 | `lat_p50/p95`、`infra`（`ok` / `api_jitter` / `api_slow`）——区分"任务难"和"API 慢" |

> **`no_delivery` 这一类的由来**：失败有两种，在通过率上长得一模一样（都是 0），但归因相反。
> - **零交付**（`writes_ok == 0`）：agent 从没进入"改代码"这一步，全程在探索/找文件/试工具。
>   这通常意味着**任务或 prompt 有缺陷**，不是 agent 能力不够。
>   t27 第一次跑就是这样：prompt 让它"查技能文档"，它没有检索工具，于是 `find /` 烧掉 8 轮，一个字没改。
> - **交付但错**（`writes_ok > 0`）：改了，但改错。这才是优化该瞄准的地方。
>
> 不区分这两者，就会把"我的 bug"记成"它不行"——而且会得出完全错误的 A/B 结论：
> 那份 base 的 0/3 里有一部分是"输在没法开始"，不是"输在不知道知识"。
> 修好 prompt 后 base 才变成干净的 `wrong_behavior`（写了代码、TTL 写短）。

### 停滞检测的真实路径验证（CLI，3 个探针）

评测脚本里跑通了不算数，得看它在真实命令行下**会不会误伤正常任务**。

| # | 任务 | 调用 | 耗时 | 结果 | 空转轮数 |
| --- | --- | ---: | ---: | --- | ---: |
| 1 | 正常任务：建 `calc.py` + 测试并跑通 | 4 | 7.5s | done | **0（未误报）** |
| 2 | 目标文件不存在（15 个模块，无 `config.py`） | 5 | 17.3s | done | **0** |
| 3 | 重构 15 个模块抽取公共基类 | 11 | 34.1s | done | **0** |

**三次零误报，这是好消息；三次零触发，这是坏消息——说明它的"靶子"很窄。**

探针 2 尤其说明问题：模型找不到文件后**主动停手并解释原因**（还说明了为什么不去
"顺手新建一个"）。也就是说，**空转不是因为任务难，而是因为"没有明确的完成判据"**：
当 agent 知道"报告找不到"也是合法结束时，它不会打转。
真正会打转的场景是——它认为事情还没做完，但看不到全貌（如 96 类那次 `41 calls / 0 改动`）。

这也解释了那个统计困境：

> **护栏的有效性取决于故障发生率，而空转是低频事件。**
> 小样本测不出显著，不是实验设计的问题，是分母本来就是小的。
> 所以护栏的对外口径只能是「最坏情况」而非「平均收益」——平均分母上大部分是零。

## 六个被自己推翻的结论

| # | 曾经的结论 | 怎么被推翻 |
| --- | --- | --- |
| 1 | 压缩省 22% token | 重复实验 n=9 后 t=0.78，与无效果无法区分 |
| 2 | 压缩能降方差 | 全量数据反证（CV 7.7% > 基线 5.7%） |
| 3 | 自适应规划提升性能 | 三批独立实验方向一致：净亏 |
| 4 | 大文件（48 类）触到能力墙 | 对照组实验：同配置 18s 通过；真因是 API 限流 |
| 5 | 压缩器"压了但没效果" | 加探针发现：**两周内一次都没真正触发**（预算漏算固定开销 698 token） |
| 6 | t26 的难度来自"真假 bug 判断" | 只删掉 prompt 里一句假完成信号，失控率 3/3 → 1/3：**一半的"难度"是我自己的 bug** |

推翻第 6 条之后，把那条规则写成了 `prompt_audit.py`——**第一次跑又在 26 个任务里抓到 2 个
同款假信号（t22、t20）**。这暴露了比单个 bug 更值得说的事：
之前所有任务质量检查都只测「判卷严不严」，没有一条测「给 agent 的信息自不自洽」。

## 面试怎么讲

核心是「**我两种都真做过，并且知道怎么证明自己对不对**」：

1. **手写 vs 框架**：先纯手写 `while` + 消息协议，搞懂 function calling 为什么要求
   `assistant(tool_calls)` 与 `tool(tool_call_id)` 严格配对；再上 LangGraph，看清框架接管了什么。
2. **参数校验是分水岭**：模型胡编参数必须**先拦再执行**，这是"工程化 Agent"和"调 prompt"的区别。
3. **怎么知道变好了**：双向校验（可解 + 严格）+ 重复消融 + 配对差值。
   单次运行的数字不写进任何结论——这个纪律是踩了三次坑之后立的。
4. **边界比数字值钱**：能说出"这个机制什么时候**不该**用"，比报一个百分比难得多。
5. **最能说明工程判断力的一条：评测集把方向带偏了**。
   Plan / 压缩 / 停滞三条线全部收益有限，收敛到同一个原因——
   **26 个任务的答案都在仓库里，所以怎么优化"使用信息"都变不出新信息**。
   发现这一点之后才做出 skill（补仓库外的知识）和 t27（答案不在代码里的任务）。
   能讲清"我的评测集在哪里失效、我怎么发现的"，比多报三个 feature 有用。
6. **诚实承认没做到的**：多 Agent 未实现；Bash 不是真沙箱；停滞检测统计上未达显著；
   Skill 检索没有向量召回（同义改写会漏），且 skill 只有 3 篇。
