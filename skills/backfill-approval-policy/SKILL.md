# 数据回刷审批规则（数据治理组）

判定是**五步固定顺序**，先命中的那条直接生效，后面的不再看。

```
plan(request, state) -> "run" | "queue" | "wait" | "reject"

第 0 步  小表且非核心      → "run"
第 1 步  当日已回刷过      → "reject"
第 2 步  窗口 > 30 天      → "queue"
第 3 步  有下游在消费      → "wait"
第 4 步  其余              → "run"
```

## 逐步说明

### 第 0 步：小表直通（最重要，也最容易漏）

条件：`row_count < 1_000_000` **且** `is_core` 为 False。

命中后**直接返回 `run`，不再执行后面任何检查**——不查当日重复、不看窗口长度、
不管有没有下游在消费。

为什么：这类回刷量小、秒级完成，走完整审批链的时间成本比回刷本身还高。
治理组的原则是「**先看这件事值不值得管，再决定怎么管**」。

⚠️ 两个条件都要满足。核心表即使只有 50 万行也**不直通**——
核心表出错的代价比多等几个小时大得多。

⚠️ 这一步必须放在最前面。放在后面就等于没有：
只要当日重复或窗口超标，就永远走不到"小表直通"。

### 第 1 步：当日重复 → 拒绝

条件：`state["same_day_backfills"] >= 1`。

返回 `reject`，**不是** `wait`、**不是** `queue`、**不是**警告。

为什么：同一天对同一张表重复回刷，会让下游看到两批互相冲突的数据，
而下游无法分辨哪批是后来的。所以第二次直接拒绝，让申请人明天再来
（这也是它和 `wait` 的区别：`wait` 是"允许，但改时间"；`reject` 是"这次不行"）。

注意阈值是 **1**，不是 2、不是 3。今天已经回刷过**一次**就够了。

### 第 2 步：窗口超过 30 天 → 离线队列

条件：`request["window_days"] > 30`。

返回 `queue`，**不是** `reject`——回刷本身是允许的，只是不能在线上时段跑。

⚠️ 边界是「**超过** 30 天」：
- `window_days == 30` → 不算超，继续往下判
- `window_days == 31` → 排队

### 第 3 步：有下游在消费 → 等到次日

条件：`state["active_subscribers"] > 0`。

返回 `wait`，**不是** `reject`、**不是** `run`。

为什么：下游正在读的分区被改写，会让它读到一半新一半旧的数据。
但回刷请求本身是合规的，所以不是拒绝，只是**错开时间**。

### 第 4 步：其余 → `run`

## 顺序为什么是这个

- **直通在最前**：它是"这件事根本不需要管"，优先级最高，命中就结束。
- **拒绝在排队之前**（v1 规定的顺序）：先判"能不能做"，再判"怎么排"。
  不能做的事，排进队列也没有意义。
- **排队在等次日之前**：排进低峰期队列当晚就能跑完，
  没必要因为下游在消费就干等到明天。**能早跑就早跑。**

## 常见实现错误

| 错误 | 后果 |
| --- | --- |
| 没有直通分支 | 小表也要走完整审批，违背治理组"先看值不值得管"的原则 |
| 直通只判 `row_count`，忘了 `is_core` | 核心表被误放行 |
| 当日重复返回 `wait` / `queue` | 下游会读到两批冲突数据 |
| 窗口阈值写成 `>= 30` | 正好 30 天的请求被误排队 |
| 有下游消费就 `reject` | 过度保守，正常回刷被卡住 |
| 先判窗口再判订阅 | 本来能当晚跑完的，被拖到次日 |
