# 数据导出审批规则（安全合规组《数据导出管理办法》）

**五步固定顺序，先命中的生效。**

```
decide(request) -> "allow" | "mask" | "review" | "deny"

第 0 步  本部门 且 内部流转        → "allow"
第 1 步  内部流转 且 含敏感字段     → "deny"
第 2 步  发往外部 且 含敏感字段     → "mask"
第 3 步  行数 > 500_000            → "review"
第 4 步  其余                      → "allow"
```

## 第 0 步：本部门内部直通

条件：`requester_dept == source_dept` **且** `target == "internal"`。

命中后**直接返回 `allow`，不再看敏感字段和行数**。

理由：数据不出部门就不设卡——本部门的人本来就有权限看，导出只是换个地方看。

⚠️ 两个条件都要满足。**只看部门就直通是这题最危险的漏**：
本部门的人往个人邮箱发数据也会被放行，而那正是数据泄露最常见的形态。

## 第 1 步 / 第 2 步：同一个字段，两个相反的结论

这是整套规则里唯一必须成对理解的地方：

| 去向 | 含敏感字段 | 结果 | 为什么 |
| --- | --- | --- | --- |
| **内部**（跨部门） | 是 | **`deny`** | 部门之间应该走数据接口。导出成文件就脱离了权限体系——文件落地之后谁拷走了都不知道，也没法回收 |
| **外部** | 是 | **`mask`** | 对外发的本来就是聚合结果，把手机号/身份证打成掩码之后可以给 |

**所以不能用"敏感字段"这一个维度统一处理。**
写成"敏感就 mask"（内部该拒的放行了）或"敏感就 deny"（对外该给的卡住了），
两种都会错一半。

顺序上，这两条都在行数判断之前：**先判要不要脱敏，再判要不要转人工**。

## 第 3 步：超过 50 万行 → 转人工

条件：`row_count > 500_000`。

返回 `review`，**不是** `deny`——大批量导出是允许的，只是要有人看一眼。

阈值是 **50 万**，不是 10 万、也不是 100 万。

## 第 4 步：其余 → `allow`

## 常见实现错误

| 错误 | 后果 |
| --- | --- |
| 没有直通分支 | 本部门内部流转也被卡，业务天天提工单 |
| 只看部门就直通 | 本部门往外发数据被放行（最危险） |
| 敏感字段统一 mask | 跨部门内部导出敏感数据被放行 |
| 敏感字段统一 deny | 对外的正常聚合数据发不出去 |
| 外部一律拒绝 | 把所有对外数据合作都堵死 |
| 行数超限直接拒绝 | 大批量导出本应转人工，不该拒绝 |
| 先判行数再判脱敏 | 大文件本来脱敏就能给，却被转去人工，白等一天 |
