# 网关限流的规定（平台组）

限流最容易错的地方不是"怎么写滑动窗口"，是**按什么计数**、**谁不该算**。
写错了本地测试全绿，只有某个大租户被打爆、或者内部流量把真实用户挡在门外时才暴露。

## 1. 配额：**每租户 900 次 / 60 秒**

**按租户计，不按用户计。** 一个租户下所有用户共享这 900 次。

> ⚠️ 这是最容易搞反的一条。直觉是"每个用户各自限流"——听起来更公平。
> 但 B2B 系统里**租户才是计费单位**：按用户算，客户开 500 个子账号就能白拿 500 倍配额，
> 等于限流形同虚设。用户级的限流是产品功能（防单人刷接口），不是平台配额。

计数用**滑动窗口**，不是固定窗口分桶（固定窗口在边界处能放过 2 倍流量）。

## 2. 内部调用**不占**租户配额

`internal=True` 的请求直接放行，不计数。

内部调用指：网关自身、批处理、监控探针、服务间调用。

> 为什么必须豁免：这些流量和用户量**不成比例**——一个大促夜的监控探针可能比真实用户还多。
> 让它们占配额，等于把自己的运维流量变成对客户的限流。

## 3. 同一 `request_id` **只计一次**（重试幂等）

客户端超时重试时会带同一个 `request_id`。重复的请求**放行但不再计数**。

> 这条最反直觉：直觉是"每次 HTTP 请求都该算一次"。
> 但客户端重试恰恰发生在**网络慢/超时**的时候——也就是配额最紧张的时候。
> 重复计费会让"越重试越被拒"形成死循环，把一次抖动放大成一次雪崩。

## 4. 超限：**直接拒绝**，返回建议等待秒数

不排队、不延迟处理。

| 做法 | 判定 |
| --- | --- |
| 排队，等窗口恢复再处理 | ❌ 积压的请求会在窗口恢复瞬间同时涌入，比拒绝更糟 |
| 静默丢弃 | ❌ 客户端会立刻重试，加重问题 |
| **返回 429 + `Retry-After`** | ✅ |

`Retry-After` = 距离窗口里最老那条记录滑出的秒数，保证客户端在配额真正恢复后才重试。

## 排查口诀

- 某个大租户总被限流、其它租户很闲 → 查是不是按用户限流，配额被"人均"稀释了
- 大促期间用户被大量限流 → 查内部调用有没有占配额
- 网络抖动后限流雪崩 → 查重试有没有重复计费
- 限流恢复瞬间服务被打挂 → 查是不是排队而没有直接拒绝
