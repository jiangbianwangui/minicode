# 埋点上报的规矩（数据平台规定）

埋点最容易出的不是技术错误，是**判据选错**：该丢的走了清洗，该忽略的走了拒收。
这类错误永远不会报错——只会让某次发版之后，报表数字**静默少了三成**，而且没人知道从哪天开始的。

## 1. 必填只有 **3 个**：`event_name`、`user_id`、`ts`

其余字段（`order_id`、`amount`、`pay_channel`、`page_id`、`referrer`…）**全是选填**。

> ⚠️ 反直觉点：直觉是"字段越多越完整，该多要求几个"。
> 实际相反——**每多一个必填，就多一条「上游某个版本漏传 → 整条数据丢弃」的链路**。
> 缺一个选填字段的数据仍然可用；缺一个必填字段的数据整条没了。
> 所以必填集合要小到不能再小，宁可下游做关联补全。

缺任何一个必填字段 → **整条丢弃**，不做部分上报。

## 2. 值里出现非 ASCII 字符（中文文案）→ **整条丢弃**

不是"把这个字段清掉再上报"，是**整条不要**。

> 为什么不能清洗：清洗后的数据是"半条真半条假"——下游看到这个事件，
> 会以为它**本来就没有**这个字段，而不是"这个字段被 SDK 吃了"。
> 两种情况下游的处理完全不同，而清洗让它们长得一模一样。
>
> 真正的修法是让上游改埋点（传码不传文案），而不是让 SDK 悄悄替它圆场。

**判定方式**：字段值里出现任何码点 > 127 的字符即视为文案。
不要试图判断"这是不是业务文案"，代价是会把正常的中文用户名也一起拦掉——
但那是**上游不该把用户名放进埋点**，属于同一个问题。

## 3. 没见过的字段 → **静默丢弃，事件照常上报，不告警**

| 做法 | 判定 |
| --- | --- |
| 整条拒收 | ❌ 客户端埋点版本比 SDK 迭代快，会把新版本数据全丢 |
| 原样透传 | ❌ 下游 schema 会漂移，一年后没人知道有哪些字段 |
| **丢弃该字段、事件继续** | ✅ |

注意"静默"：**不打日志、不告警、不计数**。未知字段是常态（灰度中的新埋点），
告警会把真正的异常淹掉。

## 4. 去重窗口：**5 秒**

同一个 `(event_name, user_id)` 在 5 秒内重复上报，只保留第一条。

- 不是"下游去重"——埋点通常没有唯一键，下游去不了；
- 不是 60 秒——用户正常的连续操作（连点两次、返回再进）就在这个量级。

**窗口从「上一次被接受的上报」开始算**；被丢弃的重复请求**不刷新**窗口，
否则一直重试的事件会永远被拦在里面。

## 排查口诀

- 某次发版后数据少了三成 → 查是不是把未知字段当成了拒收
- 报表里出现半截字段的事件 → 查是不是对文案做了清洗而不是整条丢
- 埋点量比实际操作量多一倍 → 查去重窗口是不是关着或者设太长
- 大量事件缺 order_id 之类 → 查是不是把选填字段提到了必填
