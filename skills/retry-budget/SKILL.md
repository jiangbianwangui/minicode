# 批量作业的重试预算（团队约定）

这份不是某个对端给的契约，是**我们组对"一个作业最多糟蹋多少时间"的统一约定**。
它不在代码里，也没有 lint 规则拦——违反它只会让作业从"偶发失败"变成"每次都超时"。

## 1. 最多 3 次尝试（首次 + 2 次重试）

不是 5 次。批作业是**每条记录独立重试**的，5 次 × 8000 条 = 时间直接爆表。

## 2. 退避：`0.5 * 2 ** (attempt - 1)`，**不封顶**

- 第 1 次失败后等 **0.5s**
- 第 2 次失败后等 **1.0s**

⚠️ **不要加 `min(delay, 30)` 这类封顶**。看起来"更稳健"，但上游抖动通常是
**几十秒级**的，封顶到 30 秒等于一直在抖动窗口里重试，全公司同频打过去。

## 3. 只有这些错误值得重试

| 类别 | 重试？ |
| --- | --- |
| 超时 / 连接错误 | ✅ |
| HTTP 429 | ✅（但必须优先尊重 `Retry-After`） |
| HTTP 5xx | ✅ |
| HTTP 4xx（除 429） | ❌ 重试不会变好 |
| **HTTP 422** | ❌ **尤其不要重试**，这是数据本身的问题，重试 3 次只是把坏数据处理 3 遍 |

## 4. `Retry-After` 优先，但上限 60 秒

响应头给了 `Retry-After` 就按它等；超过 **60 秒**则**放弃这条、跳过继续下一条**，
不要让整批卡在一个 10 分钟的长 window 上。

## 5. 重试计数按「单条记录」而不是「整批」

一批里第 37 条失败重试，不影响第 38 条的计数。整批共用一个计数器会导致
后面的记录无端少重试机会。

## 排查口诀

- 作业整体超时、单条都"看起来没问题" → 查是不是把 4xx 也重试了
- 全公司同时被限流 → 查有没有给退避封顶
- 同一批数据每次处理结果不一致 → 查重试计数是不是整批共用的
