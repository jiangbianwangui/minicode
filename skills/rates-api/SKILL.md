# 汇率 API（api.example-rates.com）使用约定

这份约定由**对端服务方**给出，不在本仓库代码里，也没有写在任何注释里。
写涉及该 API 的代码前必须先看这里，否则会踩下面三个坑——而且**本地测试全绿也发现不了**，
因为测试里的 fake 不会限你的频。

## 1. 限频：60 次 / 小时

免费档按 source IP 限频 **60 次/小时**，超了返回 `429`，并进入最长 1 小时的封禁窗口。

推论的硬要求：
- **缓存 TTL 不得低于 600 秒**（一小时 60 次 → 平均每次至少隔 60 秒；
  留出重试与并发余量后，业界通行做法是按 10 分钟起）。
  TTL 写 60 秒看起来"更实时"，但会把配额打满——**这是本仓库历史上出过的一次线上事故**。
- 不要在循环里对同一 pair 反复取值，先查缓存。

## 2. 重试：只重试 5xx，绝不重试 429

| 状态 | 含义 | 该怎么做 |
| --- | --- | --- |
| `429` | 你超限了 | **不要重试**。重试会延长封禁窗口，越试越久。直接抛出让上层决定 |
| `5xx` | 对端故障 | 可以重试，指数退避（0.5s / 1s / 2s），建议最多 2–3 次 |
| 网络超时 | 链路问题 | 同 5xx |

**最常见的错误写法**是把"所有异常都重试 3 次"——遇到 429 时这会把 1 小时的封禁变成 3 小时。

## 3. 时间戳 `ts` 是秒级，不是毫秒

响应里的 `ts` 是 **秒级 UTC Unix 时间戳**（10 位数字，如 `1700000000`）。

- ✅ 正确：`datetime.fromtimestamp(ts, tz=timezone.utc)` → 2023-11-14
- ❌ 错误：当成毫秒去 `/1000`，或者传给 `utcfromtimestamp` 前乘 1000 → 落到 1970 年

这个坑特别隐蔽：**只做类型转换不报错，值却是错的**，只有把结果展示给人看的时候才会发现。

## 4. 响应字段

```json
{"pair": "USD/CNY", "rate": 7.2413, "ts": 1700000000}
```

`rate` 是 float，`ts` 是 int。没有 `date` 字段，别臆造。
