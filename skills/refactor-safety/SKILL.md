# 重构安全检查清单

本仓库有过两次"重构后线上出问题"的记录，都是下面第 1 条和第 3 条没做。

## 1. 改名前先枚举调用点，别相信 IDE 之外的直觉

**必做**：`grep -rn "<old_name>" .`，然后**逐条读**命中行，判断它是：
- 定义（要改）
- 调用/导入（要改）
- **字符串里出现的名字**（如日志、配置、序列化字段 —— **往往不能改**）
- 注释/文档（改不改都行，但漏改会误导后人）

最后一条是主要事故来源：把 `"calc_total"` 这种写进配置或 JSON 字段的字符串一起换掉，
代码能跑、测试能过，但线上读取旧配置的实例全挂。

## 2. 重命名后必须验证"旧名字零残留"

```bash
grep -rn "calc_total" . --include=*.py --include=*.json --include=*.yaml
```

**测试全绿不足以证明改名完成**——测试只覆盖被测到的路径。残留的旧名字在没测到的分支里照样崩。

## 3. 先找到"不可回滚点"，再动手

不可回滚点 = 一旦写下去，就没法靠改代码撤回的操作：
- 写数据库 / 发消息 / 调用外部计费接口
- 删除文件（尤其是别人还在引用的）
- 修改被外部系统消费的格式（CSV 列名、API 字段）

**顺序要求**：不可回滚的操作放在最后一步，且此前所有纯计算的部分必须已验证通过。

## 4. 抽取公共逻辑时，先确认"真的相同"

两段长得像的代码，可能只是**恰好现在相同**：
- 它们的变更原因是否一样？（一样才该合并，否则会变成"一处改、两处坏"）
- 参数化之后，调用方需要传的参数量是不是反而变多了？

**判据：抽取后如果调用方需要额外传 3 个以上的开关参数，说明它们本来就不是同一个东西。**

## 5. 大文件改动：改完立刻跑一次语法检查

```bash
python -m py_compile <file>
```

比跑测试快得多，能在几十处改动里第一时间发现括号/缩进写坏。
大文件里 `EditFile` 的定位错误往往表现为"替换成功了但位置不对"，编译检查能挡住其中一部分。
