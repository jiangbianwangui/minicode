# SLA 等级的超时预算（平台组规定）

这份是**公司内部规定**，不是行业标准。数值换个公司就完全不同，
所以**只能查，不能推**。违反它不会报错——线上只会表现为"P0 请求转圈 8 秒才失败"。

## 1. 预算表：等级越高，预算越**短**

| 等级 | 预算 | 典型场景 |
| --- | ---: | --- |
| **P0** | **800 ms** | 收银/下单等前台主链路 |
| **P1** | **2500 ms** | 后台管理、报表 |
| **P2** | **8000 ms** | 离线任务、可延迟的批量 |

> ⚠️ **这是最容易搞反的地方。** 直觉是"P0 最重要 → 多给点时间"，实际相反：
> P0 面向前台用户，**宁可快速失败并降级，也不让用户对着转圈等 8 秒**。
> 预算给长了测试照样全绿，只有线上体验崩。

## 2. 未知 / 缺失等级 → 按 **P1**

不是最宽松的 P2，也不是最严的 P0。理由：

- 给 P2 → 未知流量白拿最宽松待遇，配额被吃掉；
- 给 P0 → 未知流量的正常请求会被误杀，误伤面太大；
- **P1 是中间档**，误判成本最低。

## 3. 降级阈值：用掉 **70%** 就走降级

不是 80%、也不是 90%。

剩下的 30% 是留给**降级路径本身**的——降级不是免费的，它要查兜底缓存、
要走备用链路、要把响应重新组装。等到 95% 再降级，降级本身就会超时。

| 写法 | 判定 |
| --- | --- |
| 90% 降级 | ❌ 降级路径没时间跑完 |
| 80% 降级 | ❌ 通用做法，高负载下仍会踩线 |
| **70% 降级** | ✅ |

## 4. 重试次数：等级越高，**越不重试**

| 等级 | 重试次数 |
| --- | ---: |
| P0 | **0** |
| P1 | 1 |
| P2 | 2 |

> ⚠️ 第二个容易搞反的地方。P0 不重试不是"不重视"，而是
> **重试会让用户等待翻倍**，P0 要的是"一到阈值立刻降级"，把确定性交给兜底逻辑。
> 重试次数多的反而是 P2——它有的是时间。

## 排查口诀

- P0 请求大量超时但下游健康 → 查预算是不是被"照顾"成了长超时
- 用户端 P0 转圈很久才报错 → 查 P0 是不是配了重试
- 高负载时降级没生效、反而整体雪崩 → 查降级阈值是不是设成了 80/90%
- 未知来源的流量把配额吃光 → 查未知等级是不是落到了 P2
