# 临时提权审批规则（权限治理组）

**五步固定顺序，先命中的生效。**

```
decide(req, ctx) -> "grant" | "grant_staged" | "review" | "deny"

第 0 步  只读 且 ≤ 4 小时          → "grant"
第 1 步  角色是 admin              → "deny"
第 2 步  时长 > 12 小时            → "grant_staged"
第 3 步  生产 且 无第二审批人      → "review"
第 4 步  其余                      → "grant"
```

## 第 0 步：只读短时直通

条件：`role == "read"` **且** `hours <= 4`。

命中后**直接 `grant`，不再看后面任何检查**——不查环境、不查第二审批人。

理由：只读改不了数据，看错了也留不下痕迹。排障时等人审批的那半小时，
故障还在扩大。治理组的原则是「**能读不能写的事，别用审批拖时间**」。

⚠️ 两个条件都要满足。⚠️ 这一步必须放在最前面，放后面等于没有。

⚠️ 生产环境也直通。直觉是"生产一律要审"，但只读 + 短时的影响面是零改动。

## 第 1 步：admin 申请 → 拒绝

条件：`role == "admin"`。

`deny` 而不是 `review`——提权到管理员**不走这条审批流**，
它有单独的流程、更重的签署和事后审计。让它在普通审批流里被"复核通过"，
等于给了一条绕过正式流程的路。

短时长、有第二审批人，都不能放行。

## 第 2 步：超过 12 小时 → 分段授予

条件：`hours > 12`。

`grant_staged` 而不是 `review`——时长本身不构成风险，
问题是**没人会盯着那么久**。先授予前一段（4 小时），到期由系统再判一次，
比让人干等审批更安全，也更快。

边界是**超过** 12 小时：正好 12 小时不算超。

## 第 3 步：生产 + 无第二审批人 → 转人工

条件：`ctx["env"] == "prod"` **且** `second_approver` 为 False。

只到这一步的申请，意味着：不是只读（或已超 4 小时）、不是 admin、也没超过 12 小时。
剩下唯一的风险点就是**生产环境上只有一个人说了算**。

## 第 4 步：其余 → `grant`

预发环境、或生产环境有第二审批人 → 直接授予。

## 常见实现错误

| 错误 | 后果 |
| --- | --- |
| 直通放最后 | 永远走不到（撞上生产环境检查） |
| 直通只看时长不看角色 | 写权限 4 小时被放行到生产 |
| 直通只在非生产生效 | 排障时最需要的那条路被堵死 |
| admin 转人工 | 给了绕过正式流程的口子 |
| 超过 12 小时转人工 | 本该分段授予，却卡在审批里 |
| 边界写成 `< 12` | 正好 12 小时的申请被分段 |
