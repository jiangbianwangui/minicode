# 告警静默审批规则（告警治理组）

**五步固定顺序，先命中的生效。**

```
approve(rule, ctx) -> "apply" | "schedule" | "review" | "reject"

第 0 步  单条规则 且 ≤ 30 分钟   → "apply"
第 1 步  范围是全局              → "reject"
第 2 步  覆盖业务高峰            → "review"
第 3 步  时长 > 1440 分钟（24h） → "schedule"
第 4 步  其余                    → "apply"
```

## 第 0 步：单规则短时直通

条件：`scope == "rule"` **且** `minutes <= 30`。

命中后**直接 `apply`，不再看后面任何检查**——不查高峰、不查时长。

理由：单条规则、半小时以内，属于值班同学的日常操作，不必走审批。
这类静默影响面只有一条告警，审批的时间成本比它本身还高。

⚠️ 两个条件都要满足。⚠️ 这一步必须放在最前面，放后面等于没有。

## 第 1 步：全局静默 → 拒绝

条件：`scope == "global"`。

哪怕只有 5 分钟也拒绝。全局静默等于关掉整个告警系统——
那 5 分钟里发生的真实故障没人知道。

## 第 2 步：覆盖业务高峰 → 转人工

条件：`covers_peak` 为 True。

`review` 而不是 `reject`——高峰静默不一定是坏事（比如已知的大促压测），
但必须有人确认。

## 第 3 步：超过 24 小时 → 排期

条件：`minutes > 1440`。

`schedule` 而不是 `review`——时长本身不构成风险，
问题是它跨越那么长时间，应该挑一个有人值守的窗口执行。

边界是**超过** 24 小时：正好 1440 分钟不算超。

## 第 4 步：其余 → `apply`

服务级、非高峰、时长适中 → 直接生效。

## 常见实现错误

| 错误 | 后果 |
| --- | --- |
| 直通放最后 | 永远走不到（撞上高峰/时长判断） |
| 直通只看时长不看 scope | 全局静默 5 分钟被放行 |
| 边界写成 `< 30` | 正好 30 分钟的请求被卡 |
| 全局静默转人工 | 高危操作被交给可能误批的人 |
| 覆盖高峰直接拒绝 | 正常的压测静默被堵死 |
| 超过 24 小时转人工 | 本该排期执行，却卡在审批里 |
