> 数据：**9 个任务，base 46 次 / skill 30 次运行**（2026-11-25 审计口径）。
> 脚本：`eval/rebuild_runs.py` 重判历史 workspace → `eval/runs/main_9task.jsonl`
> → `eval/paired_stats.py` 出统计。**全程不调用 LLM，可完整复现。**
>
> ⚠️ 2026-11-25 改了口径，旧数字（base 0/31、skill 24/25）作废。原因见第七节
> ——一句话：**旧口径的分母是我手工挑的批次，而其中一批漏报了一次 base 通过。**
>
> ⚠️ 另外 t31 已移出主表（判卷修好后 base 能过 2/3，规则全是业界默认值，
> 按造题第一道闸门就不该进这个任务族）。详见第五节。

## 二、主检验

### 配对 t 检验（n=9 题，单位是题不是次）

```
均值差 = 0.877    sd = 0.217
t = 12.14    df = 8    p = 1.96e-06
95% CI = [0.710, 1.043]
```

**这个 t 值不能按字面读。** base 侧几乎全是 0，配对差就等于 skill 侧通过率，
所以它**退化成了"单样本检验：skill 通过率是否显著大于 0"**——
描述的是"skill 侧离 0 有多远"，不是"两组差多少"。

另一个信号：**95% CI 上界 1.043 > 1.0**。通过率不可能大于 1，
说明数据贴到天花板了——这是饱和迹象，不是"效果特别大"。

### 符号检验（更该引用这个）

```
skill > base: 9 题        skill < base: 0 题        持平: 0 题
单尾 p = 0.0020
```

只问"方向对不对"，不依赖分布假设，也不被天花板效应放大。
**9 次配对全部同向，p = 2⁻⁹ ≈ 0.002** —— 这是这批数据里最硬的一条。
注意它**不受口径影响**：旧口径 9/9，新口径还是 9/9。

## 三、敏感性分析

| 处理 | n | 均值差 | t | p |
| --- | ---: | ---: | ---: | ---: |
| 全部（9 题） | 9 | 0.877 | 12.14 | 2.0e-06 |
| 剔除只有 1 个检查点区分的 t35/t36 | 7 | 0.913 | 12.94 | 1.3e-05 |
| 加回 t32（base 5/5 通过的反例） | 10 | 0.789 | 7.25 | 4.8e-05 |
| 再加回 t31（判卷修好后 base 2/3） | 11 | 0.747 | 7.00 | 3.7e-05 |

- 剔除 t35/t36 后**结论不变、均值差略升** —— 这两题没有在"撑"结论，反而在拉低它。
- 加回两个反例，均值差从 0.877 掉到 0.747，**方向不变**。这是最坏情况下的下界。

## 四、必须承认的局限

### 1. base 接近 0 是**设计出来的**，但不是 0

造题时就是按"base 会失败"筛的——`t32` 就是因为 base 5/5 通过而被排除。
所以这 9 题不是随机抽样，而是**筛选后的样本**。

但"筛选"不等于"一定全败"：全部运行里 base 通过了 **2 次**（t38 一次、
另一处在检查点复查批次的 t28）。这恰好说明筛选题只保证了"大概率失败"。

> 换句话说：这个 p 值证明的是"**在我专门构造的这批题上**，skill 能救回来"，
> 不能推广成"skill 能提升一般任务 84 个百分点"。

### 2. skill 是为这些题写的（构造效度）

先造题、再补 skill，这是对的顺序；但"能补上 skill"本身成了入选条件之一。
一个盖不住的任务（校准题 t30）就被排除在统计之外了。

> 这是**机制有效性证明**，不是**效应量估计**。

### 3. 二元判卷会掩盖"部分得分"

按检查点重算（`eval/CHECKPOINTS.md`，**另一批 27 次运行**）：剔掉作废的 t31 后，
base 过 **38/126 = 30%**，skill 过 **125/126 = 99%**；base 27 次里只 1 次六条全对（t28）。

合并两批：base **73 次里通过 2 次（2.7%）**（主表 46 + 复查 27）；
skill **57 次里通过 52 次（91%）**（主表 30 + 复查 27）。

> 所以准确的说法不是"base 完全不会"，而是**"base 会一部分、但过不了关"**。
> base 平均能过三成检查点，但六条全对只有 2 次。

### 4. 样本量刚好够，没有余量

n=9 略低于配对 t 的常规下限。符号检验在 9/9 同向时 p=0.002，已经接近这种设计的极限。
**加运行次数不会改变这个上限**——符号检验看的是"几道题同向"，不是"跑了几次"。

## 六、可以对外说 / 不能说

**可以说：**

> 在 9 个"答案不在仓库里"（需要公司内部约定）的任务上，
> 无 skill 时 **46 次运行只通过 1 次（2.2%）**，有 skill 时 **30 次通过 26 次（87%）**；
> **9 次配对全部同向，符号检验 p = 0.002**。
> 每个数字都能追溯到具体运行目录，`eval/rebuild_runs.py` 一条命令重算。

**不能说：**

- ❌ "通过率提升了 84 个百分点"（base 接近 0 是筛选结果，且已贴天花板）
- ❌ "t = 12，效果极其显著"（t 被天花板效应放大，该引符号检验）
- ❌ "skill 让 agent 整体变强了"（只在这类任务上验证过）
- ❌ "base 一次都没过"（**现在有 2 次通过了**，这句话会被打穿）

**面试时更稳的说法：**

> 我做的不是"提升准确率"，是**给一个原本依赖模型先验知识的环节引入了可检索的外部知识**，
> 并且证明了在这类任务上它是**唯一能改变对错的机制**。
> 效应量我不敢给，因为样本是我筛的，天花板也已经顶到了。
> 而且我后来做了一次审计，发现连"分母"都有问题——原来那 31 次是我手工挑的批次，
> 其中一批漏报了一次 base 通过。改成"全部 46 次运行"以后，结论方向没变，
> 但数字更难看也更可信：base 2.2%，skill 87%。

## 七、2026-11-25 的审计：改了什么，为什么

### 做了什么

`eval/rebuild_runs.py`：对 `eval/workspaces/` 里 76 个历史目录**重跑判卷**
（不调用 LLM，76 个目录约 3.7 分钟），输出 `eval/runs/main_9task.jsonl`。
每条记录带 `dir`（目录名）、`bitmap`（检查点位图）、`passed`，可以逐条核对。

### 查出三件事

1. **t38 漏报了一次 base 通过。**
   目录里有 9 次 base 运行（3 批 × 3 次），主表只记了 `0/3` 那批。
   而 `EVAL.t38.base2.md` 白纸黑字写着 `1/3`，重判也确认是 6/6 全过。
   更关键的是：**`leak_audit` 零命中** —— 不是偷看，是真猜对了。

2. **"挑批次"的规则从来没写下来。**
   为什么 t34/t35 算两批（6 次）、t38 只算一批（3 次）？
   没有任何依据，只有当时的我知道。**这就是数字不可复现的根源。**

3. **分母算错过一次**（写 30，逐行求和是 31），已由 `eval/recount.py` +
   `tests/test_stats_consistency.py` 守住。

### 为什么可以把不同批次合并

看起来"3 批 × 3 次"是不同的实验条件，其实不是：
t36 的两批 skill 运行间隔只有 **4 分钟**（`202131` → `202530`），
中间不可能改 skill 或判卷 —— 失败与通过是**同一条件下的模型随机性**。
t38 的三批同样（`212456` → `212902` → `213343`，间隔 4–7 分钟）。

> 判据：**两批之间有没有改过 skill / 判卷 / 任务**。
> 改过就必须按时间切开，不能合并；没改过就是重复抽样，应该全算。

### 代价

skill 通过率从 **96%（24/25）掉到 87%（26/30）** —— t36 那 3 次失败（4/5，差一条）
以前被排除在分母外，现在算进来了。这是这次审计对结论**不利**的地方，但它更真实。

## 九、t36 查清了：失败的是**数值**，不是结构

t36 是主表里唯一 skill 只过一半的题（3/6）。查了 6 份产物，规律非常干净：

| 运行 | 位图 | 配额数值 | 结果 |
| --- | --- | ---: | --- |
| skill r0 `202131` | 01111 | **600** | 第 1 条挂 |
| skill r1 `202153` | 01111 | **600** | 第 1 条挂 |
| skill r2 `202222` | 01111 | **100** | 第 1 条挂 |
| skill r0 `202530` | 11111 | 900 | 全过 |
| skill r1 `202551` | 11111 | 900 | 全过 |
| skill r2 `202605` | 11111 | 900 | 全过 |

**5 条检查点里，4 条是结构、1 条是数值**：

| 检查点 | 类型 | skill 组通过 |
| --- | --- | ---: |
| 配额按租户共享 | **数值**（900 次/分钟） | 3/6 |
| 租户之间互相隔离 | 结构 | 6/6 |
| 内部调用不占配额 | 结构 | 6/6 |
| 同一 request_id 只计一次 | 结构 | 6/6 |
| 窗口过后恢复 | 结构 | 6/6 |

⭐ **它读到了 skill，只是没把那个数抄对。** 失败产物 `202131` 的注释写着：

> 不按 user_id 计：同一租户下的用户共享租户配额，避免"多开小号"绕过

——这就是 skill 里"按租户算，否则开 500 个子账号白拿 500 倍配额"的转述，
措辞不同说明是**理解后转述**，不是照搬。所以不是"路由没召回"，是**读到了、结构学会了、数值丢了**。

### 这件事改变了什么

1. **"骨架可迁移、参数不可迁移"多了一条主表内部的独立证据**（原来只有留出实验 n=2）。
   t36 是同一道题内部同时出现"结构 4/4 对 + 数值 3/6 对"，比跨题对照更干净。
2. **检查点等权的局限被放大了**：一个数值和四条结构规则在分数上一样重，
   但它们的难度来源完全不同——前者是"记不住一个数"，后者是"不知道规矩"。
3. **面试可以这样讲**：

> 我的 skill 文档把"每租户 900 次/分钟"写成了加粗标题，模型三次里还是写成 600、600、100。
> 但四条结构规则——按租户共享、租户隔离、内部豁免、重试幂等——六次全对。
> 所以 skill 补的是"该怎么做"，补不了"具体是多少"；后者得靠一次校验而不是一次阅读。

4. **如果想把 t36 从 3/6 提到 6/6**，正确做法不是把 900 再写一遍（已经在加粗标题里了），
   而是让 skill 里带一个**可直接执行的校验**。这个试了，结果见下一节。

## 十、给 skill 加自检的实验：通过率上去了，但不是因为"执行了自检"

2026-11-25，在 `skills/rate-limit-policy/SKILL.md` 末尾加了一节「附：配额的自检」，
里面给了一段可直接粘贴运行的 pytest（1200 次请求必须只放行 900 次），
并写明"改完 `limiter.py` 后跑一次"。

然后跑了 3 次（`checkpoint_profile.py --mode skill --tasks t36 --repeats 3 --tag sc`）：

| | 改前（6 次） | 改后（3 次） |
| --- | --- | --- |
| 位图 | 11111 ×3、01111 ×3 | **11111 ×3** |
| 配额数值 | 900 ×3、600 ×2、100 ×1 | **900 ×3** |
| 结果 | 3/6 | **3/3** |

### ⚠️ 但机制不是"它跑了自检"

三次产物的 `tests/` 目录里**都没有** `test_quota_selfcheck.py` —— 只有任务自带的
`test_limiter.py`。也就是说：**它一次都没执行那个自检。**

所以这次提升不能归因到"可执行检查"。更可能的机制是：

1. 900 在文档里从**出现一次**变成**出现两次**（正文标题 + 自检代码里的 `== 900`）；
2. 自检代码带了算式语境（`400 次 × 3 用户 = 1200`，`900` 是其中被放行的），
   比一个孤立的"900 次/分钟"更容易被核对。

### 该怎么记这件事

- **通过率 3/6 → 3/3 是真的，但 n=3，p≈0.125，不显著，只作方向。**
- ⭐ 真正值得记住的是那个负面观察：**给了可执行的自检，它也不会去跑。**
  这和项目里另外两条现象是同一类——"给了工具不用"、"说完成=命令通过但它不跑"。
  **"可执行"只对会执行的主体有价值；对不主动执行的主体，写进示例里的数字照样只是文字。**
- ⚠️ **skill 版本因此变了**：主表那 46 次 base / 30 次 skill 用的是 **2026-11-02 版 skill**。
  以后新跑的数据不能直接和主表合并，引用时要注明版本。

### 如果还想再推一步

要验证"执行自检"到底有没有用，得把自检变成**非做不可**的一步：
比如把校验挂进任务给的 `tests/`（让既有测试一开局就是红的），
或者让它成为 `pytest` 的一部分——那时"跑不跑"就不再是 agent 的选择。
代价是这又变成了"任务本身有规格"，不再是"skill 补规格"的实验。
