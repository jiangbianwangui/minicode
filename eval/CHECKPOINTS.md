# 按检查点重算：base 到底"会"多少

## 1. 为什么要做这件事

主实验用**二元判卷**（六条检查点全对才算过）。这有个副作用：
一个把五条都猜对、只错一条的实现，和一个完全乱写的实现，在统计表上是同一个数：**0**。

留出实验（[`HELDOUT.md`](HELDOUT.md)）就撞见了这件事——A 组和 B 组通过率完全一样（0/3 vs 0/3），
拆到检查点却是 **1.7/6 vs 4.2/6**。既然那里能看见，主实验里大概率也有。

## 2. 方法

`eval/checkpoint_profile.py`：跑一遍任务，然后**逐条**执行 `_CHECKS`，输出 6 位位图（1 = 通过）。
每个任务每侧跑 3 次，共 30 + 30 次运行。

```bash
python eval/checkpoint_profile.py --mode base  --tasks t27,...,t38 --repeats 3 --tag b
python eval/checkpoint_profile.py --mode skill --tasks t27,...,t38 --repeats 3
```

`--tag` 是必需的绕路：workspace 里文件多时，`rmtree` 会撞上沙箱的批量删除阈值（>50 文件），
换个后缀就绕过去了。

## 4. ⚠️ 两个必须单独说的问题

### 4.1 t31 的 base 从 0/3 变成了 2/3

主表里 t31（重试预算）记的是 base **0/3**。这次三次跑出 **6/6、6/6、3/6**，且**没有泄漏**
（`leak_audit` 三份产物都是 0 命中）。

所以这不是"它又偷看了"，是**它真的猜对了**。最可能的原因是 t31 的判卷被修过：
原来只认 `sleep=time.sleep` 一种写法、把参数化注入判成失败，后来为了让判卷不惩罚更规范的写法，
放宽了匹配——**放宽之后 base 也能过了**。

这是判卷修正的代价，之前没算进去。**t31 现在的区分度接近 0，不该再算进主表。**

### 4.2 t34 那个 6/6 没有复现

上次 base 跑出 6/6（并被抓到写了 skill 里的四个阈值，见 [`LEAK.md`](LEAK.md)），
这次三次是 **0/6、0/6、2/6**。同一条命令序列不稳定地泄漏，说明那次是一次性的偶发，
而不是"每次都读到"。结论不变：**base 不是保证没有 skill，是设计上不给。**

### 4.3 t28 也被 base 过了一次（这条比 t31 更该注意）

t28 在三次里有一次 **3/3 全过**，`leak_audit` 三份产物零命中。也就是说 **base 真的猜对过一次**。

t31 可以归因于"题不好"（六条全是业界默认值），但 t28 不是——它考的是对端契约里的
限频、ack 余量、死信，base 那一次是**蒙对的**。

这件事的意义：**「30 次全败」是一个小样本快照，不是能力上限。**
把主对照（30 次）与本次复查（剔 t31 后 27 次）合起来：base 有交付 **57 次里通过 1 次（约 2%）**。
所以对外口径只能写「base 大多做不到」，写「base 恒为 0」会在扩样本时被打穿。

## 5. 修正后该怎么讲

- 「base 有交付 31 次全败」→ **应改成「base 大多做不到，约 2% 能撞对」**：
  按检查点算（剔 t31），base 过 30%，只是几乎从不六条全对（27 次里 1 次）。
- **skill 的价值说清了**：它把检查点通过率从 30% 拉到 99%。这不是"从不会到会"，
  是**"从会一半到会全部"**——而且补的恰好是最后那几条参数。
- t31 已从主表剔除；t28 那一次要主动说，否则"全败"这个词站不住。

## 6. 局限

- base 侧 3 次仍有抖动（t28 一次全过、两次 1/3），3 次不足以给稳定估计。
- 检查点等权。一条"存在一票否决"和一条"边界值取不取等号"在分数上一样重，
  但前者显然更值钱。用位图而不加权，是为了不掺我自己的主观权重。
- 只覆盖 10 个有 `_CHECKS` 的任务；t01–t26 的判卷形态不同，没有纳入。
