## 二、结论（按"可复现度"排序）

### 1. P0「增量计划注入」是明确代码胜利：自适应 plan 税 −37%（相对）
- Batch B→C，baseline 几乎不变（134.8k→131.3k），但：
  - +AdaptivePlan：229,104 → 189,509（**惩罚 +70% → +44%**）
  - +AdaptivePlan+Compress：248,707 → 201,728（**惩罚 +84.6% → +53.7%**）
- 根因修复：旧版每轮把「整张剩余计划」重发进 system prompt；P0 改为只注入「当前步骤 + 进度 + 接下来 1-2 步预览」，
  完整计划本就在历史 plan 调用中可见。system prompt 不再逐轮膨胀 → plan 税显著下降。
- 这是可上简历/面试的实话："我实现了 Plan-Execute，消融发现每轮重发整张计划让 token 涨 70%，
  改成增量注入当前步后把惩罚降到 44%——并据此判断该模型下 plan 默认不该开。"

### 2. 但 Plan 模式（强制 or 自适应）对 deepseek-chat 仍是净成本 → 默认 OFF
- Batch C 全部 plan 模式都高于 baseline（+34%~+54%）。即使最小化注入，plan 文本 + 额外 plan 工具轮次仍净增。
- 结论：MiniCode 默认 `plan_mode=False`（已是）；`--adaptive` 仅作为可选项保留，不写进默认路径。
- 这本身是个好故事：没硬凹"plan 有用"，而是用数据证明"这个模型下 plan 不划算，故默认关"。

#### 证伪记录（falsification log，方法论资产，可直接用于面试）

> 工程里"验证一个想法不成立"和"验证它成立"同等重要。这里完整保留一次失败的假设，
> 因为**能被实验证伪的 feature 才有可信度**；只报喜的消融等于没做。

| 环节 | 内容 |
| --- | --- |
| **假设（H1）** | plan 模式有用，但只该给复杂任务开。做成自动开关（`is_complex_task` 规则门控）后，应"既拿 plan 收益，又躲开简单任务的 plan 税"。 |
| **预测** | 若 H1 成立，`+AdaptivePlan` 的总 token 应 **低于** `+Plan`（强制全开），且接近 baseline。 |
| **实验** | Batch B / Batch C 对齐消融，16 任务同端点。 |
| **实测** | `+AdaptivePlan` 在 Batch C 为 **189,509 token（+44.4% vs baseline）**，反而**高于** `+Plan` 的 175,877（+34.0%）。预测被推翻。 |
| **根因** | 计划文本每轮注入 system prompt，而压缩层当时不覆盖该块 → 开了 plan 的复杂任务 token 直接膨胀；同时模型逐步重调 `plan` 工具，多出额外轮次。 |
| **决策** | ① 保留 P0 增量注入（把自适应惩罚从 +70% 压到 +44%，仍不足以转正）；② **自适应规划默认关闭**，仅作 `--adaptive` 可选项；③ 不在简历中宣称"自适应规划带来收益"。 |
| **可复用教训** | "按复杂度门控"只在**开关本身的开销可忽略**时才有意义。当 feature 的固定开销（每轮注入）大于它节省的开销时，门控只是把税从"所有任务"转移到"复杂任务"，甚至因额外分支而更贵。 |

### 3. 压缩器：「保留文件操作精确内容」是**必要的正确性修复**，但**不足以构成净收益**（结论已在 F/G 修正）

**确定的部分（机制正确，必留）**
- Batch D（naive 摘要，连文件读/写/改轮次一起摘要）：困难桶 **+25%**、t16 步数 8→11——**灾难性失败**。
- 修复：只压"可丢"轮次（Bash/搜索/回执），**永远保留 ReadFile/EditFile/WriteFile 的精确内容**，
  + no-regret 闸门 + 真实 remaining 估算。
- **面试高频点**："为什么不直接 summarize 全部历史？" → "coding agent 靠精确字节行动，盲摘要会损害任务质量；
  必须按工具类型区分可压/不可压轮次，文件操作轮次永不压缩。"（layer1=单次截断，layer2=轮次摘要但跳过文件操作）

**被数据推翻的部分（不要写"压缩净赚"）**
- Batch E 曾显示困难桶 −12.5%、全局 −7.9%（单次运行）→ 乐观结论。
- Batch F（3×）压缩 −4.5% 但 t=0.84 不显著；Batch G（困难桶 6×）压缩 **+9.8%**；合并 n=9 后 **+4.2%，t=0.78**。
- **符号在独立实验间翻转（−22%、−7.9%、−4.5%、+9.8%）→ 该 feature 在本评测集上与"无效果"无法区分。**
- 稳定存在的只有机制副作用：**步数 +5.2%、调用 +5.4%**。压缩省下"每步重喂历史"，却诱发 agent 多走一步补信息，两者相抵。
- **根因判断**：本评测集轨迹太短（困难任务平均 7.5 步），历史重喂的成本还没累积到超过"摘要调用 + 多走一步"的开销，
  因此没跨过盈亏平衡点。压缩是**长轨迹优化**，在 5–8 步任务上本就不该期望收益。

**当前决策**：`compress` 保持默认关闭（与数据一致）。若要让它转正，需要显式做**盈亏平衡轨迹长度**实验（见下一步）。

### 4. 方法论证信（决定哪些数字能写进简历）
- **已建立重复消融能力**：`eval/repeat.py` 支持「N 模式 × R 次 × 任务集」，自动输出 mean±std、CV、每次原始值。
- **Batch F（3×3）给出的判读**：
  - `plan / adaptive` 是**净成本**——在 3 个独立批次中方向一致（+53.7%、+1.4%、+7.3%）→ **结论稳健，可写简历**。
  - `compress` 是**净收益但幅度不稳**——3 次独立实验符号全负（−22.4%、−7.9%、−4.5%），
    但 n=3 时 t≈0.84 不显著 → **只能写"持续降低 token、量级约 5~10%"，不能写精确百分比**。
  - "压缩压方差"的假设**已被证伪**，不要写。
- **Batch D→E 的困难桶 +25%→−12.5% 反转仍是机制级证据**（同会话连续、机制改动精准命中），
  它证明"保留文件操作精确内容"这一设计正确，但不负责提供精确幅度。

### Batch H（2026-10-21 22:50–23:16，**尺子改造后的首个配对实验**：2 模式 × 3 次 × 25 任务）

> 本批次的意义**不在压缩结论，而在尺子本身**。前七批的所有对比都有一个共同缺陷：
> 把一轮里 16/25 个任务的 token **相加**再横比（如 base 86,888 vs compress 95,446 = +9.8%），
> 这是"总价对比"——任务间难度差会淹没信号，且每轮只贡献 1 个样本。
> 本批改为**同任务配对差值**（同一任务跨模式作差，难度自动抵消），并新增过程层归因。

**改造内容（代码）**
- 新增 `eval/metrics.py`：过程层指标（工具序列 / 首个失败步 / 工具成功率 / 失败归类），
  只读 `RunStats`，**不改 agent.py**，避免测量逻辑污染被测对象。
  关键设计：**过程指标与 `passed` 解耦**——通过也可能有过工具报错，标 `passed_with_retry`。
- 重写 `eval/repeat.py`：配对差值 + 配对 t 检验 + 符号一致性 + 逐任务明细 + 尺子健康度自检。
- 改 `eval/runner.py`：分桶从 `t01-t10/t11-t16/t17+` 硬编码改为**按实测成本三分位**（编号大 ≠ 任务难）。

**结果（`EVAL.paired.md`）**

| 指标 | 数值 | 判读 |
| --- | --- | --- |
| 配对均值差 | **−130 ± 3,698 token / 任务（−0.9%）** | 均值远小于标准差 |
| 配对 t 检验 | **t = −0.18 (df=24)** | 远未达显著（门槛 \|t\|>2） |
| 符号一致性 | **14 省 / 9 增 / 2 平** | 不满足"省 ≥ 2×增" |
| 调用数差 | −0.04 | 几乎为零 |
| 过程层 | base 6/75 次运行含工具报错；compress 9/75 | compress **返工略多** |

**关键发现：方差几乎全部来自 14 个任务，其余 11 个任务全是噪声**
- 大涨（> +500）：t09 +1,361、**t15 +9,754**、**t16 +10,057**、t24 +672、t25 +2,123 → 合计 +23,967
- 大省（< −500）：t06 −5,956、t12 −706、t14 −1,234、t17 −789、t19 −6,104、t20 −2,826、
  t21 −4,568、t22 −807、t23 −4,536 → 合计 −27,526
- 小幅（\|Δ\| ≤ 500）共 11 个任务，合计仅 +296（**均值 +27 token**）
- → **压缩器对 11/25 个任务是精确的"零效果"；全部净差（−3,559）由 14 个任务的涨落相抵而来。**
  这正是"均值 −0.9% 却 t 不显著"的机制解释：**不是没有效应，而是效应的方向和幅度都不稳定。**

**必须承认的方法论缺陷（本批自身的不完美）**
- t15（+9,754）与 t16（+10,057）的 **Δ调用数分别为 +3.67 和 +2.00**，即 token 暴涨来自多走 2–4 轮，
  而非单轮更贵。这属于**轨迹分叉**（LLM 采样的路径不同），不是压缩器导致的。
  3 次重复无法区分"压缩引起"与"采样波动"→ **需要更大 n 或固定 seed 才能拆开**。
- 单任务 token 波动可达 ±40%（t16 base 在批次间从 17,925 到 39,888），
  因此任何"单批单任务"的百分比都不可引用。

**本批结论（可写简历的版本）**
> 用逐任务配对消融（n=25 任务 × 3 次重复、配对 t 检验）证明：分层压缩在 25 个代码修改任务上
> **净差 −0.9% 但 t=−0.18 不显著，且 11/25 个任务精确零效果**；全部净差由 14 个任务的
> 双向涨落相抵而来。据此判定该优化**与"无效果"不可区分**，默认关闭，
> 并把"压缩是长轨迹优化、需跨盈亏平衡步数"作为边界结论。

### Batch I（2026-10-22，**难度扫描**：不再猜难度，改为扫难度）

> 完整报告见 **`EVAL.sweep.md`**（扫描器：新增 `eval/sweep.py`）。
> 本批解决的是 Batch H 遗留的那个红色警告：**「时过时不过」的任务一个都没有** —— 任务难度分布两极。
> 做法不是"再造更难的题"（那只能靠猜），而是**把难度当连续旋钮扫**。

**实验设计：两个旋钮必须分开**

| 维度 | 固定 | 变化 | 测什么 |
| --- | --- | --- | --- |
| `size` | 6 类 / 12 个修改点 | 每组样板方法数 → 文件 500→10,160 行 | 上下文压力 |
| `count` | 总行数 ≈6000 | 类数 → 修改点 4→48 处 | 覆盖广度 |

`count` 用反推公式固定总行数（5982–6176 行），做到「规模不变、只变修改点数」。
**这是本次与以往所有批次的关键区别**：以前把"文件大"和"要改的地方多"混在一起，无法归因。

**11 档全部通过「初始必败 + 参考解必过」双重校验**，且失败原因都是正确的那种
（"审计标记应 N 处，实际 0"），不是行数异常导致的假失败。

**结果：两个维度都扫到饱和，一条直线（限 24 类 / 48 处以内）**

| 维度 | 跨度 | 通过率 |
| --- | --- | --- |
| size | 500 → 10,160 行（20×） | 12/12 = **100%** |
| count | 4 → 48 处修改点（12×，最多 24 类） | 10/10 = **100%** |

> 再往上（48 类 / 96 处、96 类 / 192 处）通过率开始不稳且不可复现 —— 见下文补测。

**决定性发现（本批真正的产出）：agent 用的是"定位式 + 脚本化"，不是"通读式"**

- **`token/行` 随规模单调下降 7.5 倍**（53.77 → 7.14）——定位成本是常数量级，被规模摊薄。
- 24 类 / 48 处修改只用 12 次调用。查工具序列：
  ```
  12 类：Bash → ReadFile → Bash → Bash → Bash → Bash → Bash → Bash → Bash
  24 类：Bash → Grep → ReadFile → Bash → Bash → ... → Bash
  ```
  **全是 Bash，没有一个 EditFile。** 它在重复修改时**主动升级为写脚本批量处理**。
- count 维度成本涨 248%、调用涨 89%（28k→98k token），但**通过率不掉**
  → **难度压力转化为成本，而不是错误。**

**这条发现同时解释了此前所有"feature 没用"的结论（重要）**

> 分层上下文压缩想治的病是"每轮重发历史 → token 膨胀"。
> **但这个 agent 根本不把大内容装进上下文 —— 它 Grep 定位、Bash 跑脚本。病不存在，药自然无效。**

所以 Batch F/G/H 反复测出「压缩与无效果不可区分（n=9 t=0.78；n=25 t=−0.18）」，
不是压缩器写得差，而是**它针对的问题在这个 agent 的工作方式下不存在**。
Plan-Execute 净亏同理：任务已被"定位 + 脚本"两步解决，再加一层规划只是加税。

**上探 48 类：我先提出的 `max_obs` 假设，被自己的对照实验证伪了（同日 21:50–22:05）**

第一次 48 类（96 处）单次运行 **>28 分钟仍在执行，人工终止**。当时的推断是：

- `repos.py` 的 mtime 仍是 setup 时刻 → 28 分钟一个字节没写进去，卡在动手之前；
- verbose 复现：第 2 步 `grep -n "class"` 被 `…（输出过长，已截断至 2000 字符）` 在
  `Entity43Repo` 处截掉；
- 实测各档 grep 输出：12 类 727 字符 / 24 类 1,455 字符 / **48 类 2,909 字符**
  —— 断点恰好落在 2000 这条线上。

证据链非常"漂亮"。然后做对照实验：

| 实验 | `max_obs` | `max_iter` | 耗时 | 结果 |
| --- | ---: | ---: | ---: | --- |
| A | **2000** | 12 | **18.4s** | ✅ 通过（11 calls） |
| B | **8000** | 12 | 23.1s | ❌ 预算耗尽（13 calls） |
| C | **2000** | **60**（复现卡死配置） | **24.2s** | ✅ 通过（10 calls） |

**三个结果全部与假设相反。** `max_obs=2000` 完全够用；调到 8000 反而更差
（塞进更多 observation → 轨迹变长、还开始尝试 `WriteFile` 全量重写）。

真因：**API 侧延迟**。当时 `RunStats` 只有 `total_seconds` 一个总账，
无法区分"模型在想"和"网络在排队"。**已修复**：新增 `llm_latencies`（逐次往返秒数）
与 `latency_stats()` 判读（`ok` / `api_jitter` / `api_slow`）。
今天实测 p50 = **1.1–1.5s**，与昨晚差两个数量级 —— 昨晚是限流，不是任务难。

**48/96 类补测：三轮 16 次，通过率不稳且不可复现**

| 轮次 | 48 类（96 处） | 96 类（192 处） |
| --- | --- | --- |
| 第 1 轮 | 1/2 | 2/2 |
| 第 2 轮 | 3/3 | 2/3 |
| 第 3 轮 | 2/3 | 3/3 |
| **合计** | **6/8 = 75%** | **7/8 = 87.5%** |

**规模更大的档通过率反而更高；同档跨轮波动（1/2→3/3→2/3）大于档位间差异。**
→ `count` 维度**不存在单调难度关系**，"48 类断点"是拿一次异常运行画出的假点。

**失败模式是两种不同的病（新发现）**

| 档位 | 模式 | verify 原文 | 含义 |
| --- | --- | --- | --- |
| 48 类 | **改多了（差 1 处）** | 应 48 处，实际 49 | 把基类 `_Base` 也当成仓库类 → **语义辨析错误** |
| 96 类 | **未动手（探索循环）** | 应 96 处，实际 0，却烧 41 calls / 358k token | 探索吃光预算，一处未改 → **策略失效** |

同档成功只要 10–12 calls，失败要 19–41 calls。差别不在规模，在**这一轮有没有一次想对策略**。
这也顺带解释了 Batch F/G/H 里 t15/t16 的"轨迹分叉"——不是压缩引起，
`temperature=0` 也不保证服务端推理确定性。

**一个反向结论（本轮唯一否掉自己上一版的地方）**

> **随机的区分度不能当评测资产。**
> 同样配置、同样 `temperature=0`，这次过下次不过 → 它测的是抽样运气，不是能力。
> 拿它做 A/B，基线组和实验组的差异会被 ±25% 的随机波动淹没
> —— 这正是 Batch F/G/H 里反复出现"方向相反、t 值极低"的机制。

**战略结论**

> **"机械式批量修改"这个任务族已经饱和。不要再加量，要换任务性质。**
> 凡是"重复 N 次同一个动作"的题，都会被一个 Bash 脚本吃掉。
> 能制造区分度的难度必须**不可脚本化**：每处改法不同 / 需判断该不该改 /
> 规则只能从测试反推 / 有方案取舍。

**对既有评测集的修正**
- t25（5960 行审计改造）**已被证明是"简单题"**——规模大但可脚本化，不该再当"困难任务"引用。
- t20（大文件 10 处调用点改造）同理，难度被高估。
- **"困难桶"标签需要按本次扫描重新校准。**

**本轮的方法论污点（如实记录）**
1. **把一次异常运行当成了规律。** 并且为假设"找旁证"（量各档 grep 长度），
   那不是验证，是确认偏误。教训：**单次异常只能提出假设；验证必须改一个变量做对照。**
2. `count` 在高档位无法严格固定总行数（类离散：48 类 5,624 行 / 96 类 7,880 行），
   所以 48 vs 96 的差异不能当因果关系。
3. 同一档三轮 1/2、3/3、2/3 → **任何基于单次运行的 A/B 对比都不可信**；
   本轮 n=8 仍偏小，75% / 87.5% 的区间很宽，只支撑"不单调"这个方向性判断。

### Batch J（2026-10-23，**造"不可脚本化"任务**：真假 bug 混排 → 没造出稳定失败，却找到了噪声主源）

**动机**：Batch I 的结论是"机械式批量修改已饱和"，凡是"重复 N 次同一动作"的题都会被一个
Bash 脚本吃掉。于是造 t26：三处真 bug 修法互不相同 + 两处"看起来像 bug 其实是外部对接约定"，
规则只写在 docstring / `INTEGRATION.md` 里，既有测试恰好只覆盖不触发 bug 的区间。

**任务设计（`eval/tasks/t26_billing_intent.py`，10 个 py + 1 份对接说明 + 测试目录，210 行）**

| 类型 | 内容 | 线索来源 |
| --- | --- | --- |
| 真 bug 1 | 阶梯计价把"全部用量"按第二档算 | `rating.py` docstring：「仅超出部分」 |
| 真 bug 2 | 按月折算把天数硬编码 30 | `proration.py` docstring：「当月总天数」 |
| 真 bug 3 | 导出把"分"当"元"格式化 | `models.py` 金额约定 + 字段名 |
| 假 bug 1 | 税额 `int()` 截断 | `tax.py` docstring + `INTEGRATION.md` §2 + `legacy_recon.py` 依赖 |
| 假 bug 2 | 负用量返回 0 而不报错 | `rating.py` docstring + `credit_note.py` 调用方 |

**双向校验**：✅ 初始必败（`('101', 3029)`）/ ✅ 参考解必过 / ✅ 既有测试初始 `4 passed`
（bug 全被测试掩盖，跑测试发现不了，必须读文字）。

**实测：没达到验收标准**

| 配置 | 通过率 | 说明 |
| --- | --- | --- |
| `max_iter=25` × 3 | **1/3** | 2 次失败均为 `max_iter` 耗尽，不是"改错了" |
| `max_iter=40` × 3（探针） | **3/3** | 11–17 次调用，两处假 bug 都正确保留 |
| `max_iter=40` × 5（base） | **2/5** | 3 次跑满 40 步 |
| `max_iter=40` × 5（compress） | **2/5** | 3 次跑满 40 步 |

按我们自定的验收标准（**连续 3 次稳定失败且原因一致**），t26 **不合格**：
它是"时过时不过"，不是可供 A/B 的稳定地形。**不把它当作边界任务引用。**

**真发现 ①：agent 会切换策略，昨天的结论要加限定条件**

| 任务族 | 工具序列 | 工作方式 |
| --- | --- | --- |
| t25（5960 行，机械批量改） | `Bash→Grep→Bash→Bash…` | **定位 + 写脚本**，从不整读 |
| **t26（210 行，需判断）** | `Bash→ReadFile×12~13→Bash×4→EditFile×3` | **先通读全部文件，再动手** |

Batch I 的结论「agent 不把大内容装进上下文，所以压缩器无病可治」**只对机械批量修改类任务成立**。
在需要语义判断的任务上，它确实会通读——上下文压力是真实存在的。

**真发现 ②：压缩器在 t26 上仍然无效，原因是设计死结**

t26 代码量只有 t25 的 1/28，token 却是它的 1.5–3 倍（68k–657k vs 45k）。但
`PRESERVE_TOOLS` 含 `ReadFile`，**通读产生的内容全部不可压缩**。
于是形成死结：

> 能压的（对话、报错、Bash 输出）省得少；该省的（文件内容）为了正确性不能压。
> **压缩器的收益空间被它自己的安全设计吃掉了。**

**真发现 ③（本轮最重要）：轨迹是"双峰"的，这才是 A/B 测不出效应的根因**

10 次运行按 token 分布，不是正态，而是清清楚楚的两峰：

| 簇 | 次数 | 均值 token | 工具步数 | 含义 |
| --- | ---: | ---: | --- | --- |
| 快路径 | 4 | **66,331** | 11–17 | 想通策略，一路改完 |
| 空转 | 6 | **410,118** | 39–40（跑满） | 没想通，探索循环烧光预算 |

**相差 6.2 倍。** 同一任务、同一配置、同一 `temperature`，差别只在"这一轮有没有想对"。

这解释了 Batch F/G/H 的全部现象：**不是效应小，是方差来源是策略分叉**。
一个 18% 的优化效应，被 6 倍的路径方差完全淹没，怎么加 n 都测不出来
（除非 n 大到能分层）。

**结论（决定下一步）**

> **在"空转"被治理之前，任何 A/B 都不可能显著。**
> 先让 agent 的行为可复现（缺的是**停滞检测**：连续 K 步没有成功的文件写入 → 判定空转），
> 再谈难度、再谈优化。

这条把 Batch I 的"换任务性质"和 Batch H 的"加大 n"都降级了——它们都不是瓶颈。

### Batch K（2026-10-23，**停滞检测**：治 Batch J 暴露的"空转"，第一次把方差压下来）

**动机**：Batch J 量出 token 分布是双峰的（快路径 66k / 空转 410k，差 6.2 倍），
这 6 倍方差把所有 A/B 效应都淹没了。所以先治空转，再谈优化。

**设计（`stall.py`）—— 判据不是"有没有写文件"**

这一点是全篇关键：解题前连续读 12 个**不同**的文件是完全正常的推进
（t26 快路径就是 `ReadFile×13` 才动手），绝不能算空转。判据改为：

| 本轮发生的事 | 判定 |
| --- | --- |
| 出现一个**之前没见过的**读/搜/命令签名 | 有进展，idle 归零 |
| 有**成功的**写操作（WriteFile/EditFile） | 有进展，idle 归零 |
| 两者都没有（重复读同一文件 / 重复同一条命令 / 全部失败） | idle +1 |

动作两级：连续 `warn_after=6` 轮无进展 → 往 system 注入一次进度警告
（**加在 system 而不是追加 messages**，避免伪造用户消息、破坏 tool_call 配对）；
警告后仍无进展到 `stop_after=10` 轮 → 终止，`status="stalled"`。

**实测（t26，`max_iter=40`，base vs stall 各 5 次，同批次）**

| 模式 | 5 次 token | 通过 | 平均工具步 |
| --- | --- | ---: | ---: |
| base | 705,871 / 490,558 / 369,024 / 66,611 / 101,110 | 2/5 | **40.2** |
| stall | 134,692 / 86,692 / 82,492 / 79,661 / 122,246 | **3/5** | **27.2** |

| 指标 | base | stall | 变化 |
| --- | ---: | ---: | --- |
| 均值 token | 346,635 | 101,157 | **−70.8%** |
| 最坏 token | 705,871 | 134,692 | **−81%** |
| 次坏 token | 490,558 | 122,246 | −75% |
| 极差（max/min） | **10.6×** | **1.7×** | 方差收敛 6 倍 |
| 失败归类 | `max_iter`×3 | `stalled`×2 | 归因变清楚 |

**扩到三类任务后，规律出来了（这才是结论）**

| 任务 | 任务性质 | base 均值 | stall 均值 | 变化 | 通过（base→stall） |
| --- | --- | ---: | ---: | ---: | --- |
| t20 | 大文件 10 处改造，脚本化、短轨迹 | 18,556 | 18,486 | **−0.4%** | 3/3 → 3/3 |
| t25 | 5960 行审计，读得多、有返工 | 88,721 | 46,807 | **−47.2%** | 3/3 → 3/3 |
| t26 | 真假 bug 混排，需判断、易空转 | 346,635 | 101,157 | **−70.8%** | 2/5 → **3/5** |

> **收益与该任务"本来会不会空转"严格正相关。**
> 不会空转的任务上，护栏**零影响**（t20 −0.4%，t=−0.02）；
> 越容易失控，削掉的越多（−47% → −71%）。
> 这正是护栏该有的性质：**只在会出事的地方生效，不打扰正常路径。**

**⚠️ 统计上仍不显著，不能吹**

| 检验 | t | df | 临界值（双尾 .05） | 结论 |
| --- | ---: | ---: | ---: | --- |
| t20 配对 | −0.02 | 2 | 4.303 | 不显著（本就没效应） |
| t25 配对 | −2.82 | 2 | 4.303 | 不显著（n 太小） |
| t26 配对 | **−2.11** | 4 | 2.776 | ❌ 不显著 |
| t26 Welch | **2.03** | 4.1 | ≈2.78 | ❌ 不显著 |
| **11 次配对合并**（相对变化率） | **−2.21** | 10 | **2.228** | ❌ **差 0.018，边缘不显著** |

合并后均值 −29.8%、标准差 44.8、符号 8 省 / 3 增。p 约 0.05。
**所以「−70.8%」「−29.8%」都不能作为结论引用，只能称为强趋势。**
再加大 n 多半能过线，但那就是"跑到达标为止"，不是科学——**所以我停在这里，改用机制与最坏情况说话。**


**那为什么仍认为它是真效果：三条不依赖 p 值的机制证据**

1. **平均工具步 40.2 → 27.2**：base 的 3 次失败全是"跑满 40 步"，
   stall 的失败变成 `stalled`（被提前拦下，9–11 步就终止）。**失败形态变了，不是数字抖动。**
2. **极差 10.6× → 1.7×**：一个纯噪声的改动不会把分布从十倍差压到 1.7 倍差。
3. **最坏/次坏同时降 81% / 75%**：不是单点离群值拉动均值，是两个坏样本一起被砍。

**正确的评价口径（这是这轮最该记住的）**

> 停滞检测是**护栏**，护栏的价值在"最坏情况"，不在"平均值"。
> 用均值评价护栏，是用错了尺子——这和 Batch H 用平均 token 评价压缩器是同一个错误。

所以对外只写：**「最坏情况 token −81%，轨迹方差收敛 6 倍」**，
不写「平均 −70.8%」，更不写「显著提升准确率」（3/5 vs 2/5 在 n=5 下毫无统计意义）。

**防误报验证（单测 `tests/test_stall.py`，9 条）**
- 连续读 13 个不同文件 → 全程 `idle=0`，不警告 ✅（这是最容易误杀的场景）
- 重复读同一文件 → 第 4 轮警告 ✅
- 写成功后 idle 归零 ✅
- 工具失败不算进展 ✅
- Bash 命令各不相同（写脚本批量改）算进展 ✅；空格归一化后同一条命令算空转 ✅
- 集成：`stall=True` 时真的提前终止（`llm_calls < 12`）✅
- `stall=False` 时行为与改造前完全一致（可插拔）✅

**残留问题**

1. **合并 t 差 0.018 没过线**（−2.21 vs 2.228）。这是实话：**它是强趋势，不是已证实的效应。**
   要坐实只有两条路：(a) 加大 n 到 20+ 配对；(b) 找一个**本来空转率更高**的任务族
   （比如需要读外部报错再定位的 debug 类），让效应量本身变大而不是靠样本量。
2. **快路径是否有额外开销未测**：stall 组最好 79,661 vs base 最好 66,611，但区间重叠，
   无法判断是"警告提示的 token 成本"还是采样噪声。
3. `context.py` 的 `PRESERVE_TOOLS` 里有三个**不存在的工具名**
   （`ViewFile` / `ReadLines` / `GrepFile`，真实工具叫 `Grep`）→ 保护规则实际只覆盖
   3 个工具。**本轮未修**，因为改它会变动压缩行为、污染 A/B。

### Batch L（2026-10-23 夜间，**审计压缩器是否真的在跑** → 发现它从未触发）

**动机**：Batch K 把方差压下来后，想给压缩器一次公平机会。但在跑 30 分钟 A/B 之前，
先花 1 分钟问了个更便宜的问题：**它到底有没有压缩？**

**探针结果（t26，compress 模式，13 次调用）**

```
compress() 被调用 12 次，真正触发 0 次，共省 0 字符
```

逐轮预算追踪（`est_tok` = 压缩器自己以为的上下文大小）：

| est_tok | 阈值 | 触发 | 挡住它的闸门 |
| ---: | ---: | --- | --- |
| 79 → 3983 | 4000 | no | `tokens <= 阈值 4000` |
| **4028**（第 21 轮） | 4000 | **YES** | 修好后首次触发 |

**它一路爬到 3983 就到顶了，永远差 17 token 碰不到 4000。** 而这次运行实际烧了 **97,209 token**
（平均每次请求 7,478）——估算值和真实值差一倍多。

**根因（两个叠在一起的漏算）**

1. **固定开销没进预算**：`_node_agent` 里 `extra = estimate_tokens([sys_msg]) if self._use_plan else 0`,
   非 plan 模式下 `extra = 0`；**工具 schema（6 个工具的 JSON，521 token）从来没被计入过**。
   合计漏掉 698 token/次。
2. **估算系数对中文偏乐观**：`estimate_tokens` 用 `len // 4`，中文/代码混合实际约 `//2.3`，
   系统性低估约 1.7 倍（真实 7,478 vs 估算 4,000 量级）。

**修复**：`self._tool_tokens` 在构造时算一次，`_node_agent` 里
`extra = estimate_tokens([sys_msg]) + self._tool_tokens`（不再区分 plan 模式）。
新单测 `tests/test_compress_budget.py` 两条，锁死「预算必须覆盖固定开销」。

**修复后重测（t25，5960 行，可压缩轮次最多，`max_iter=30`，各 3 次）**

| base | 114,046 / 74,045 / 26,989 | 通过 3/3 |
| --- | --- | --- |
| compress | 28,459 / 58,734 / 75,570 | 通过 3/3 |

均值 −24.3%，但**配对 t = −0.45**（df=2），符号 2 省 / 1 增，其中一次是 **+180%**。
→ **压缩器这次真的启动了，效果仍然不可复现。**

**这个发现推翻了什么**

Batch F/G/H 关于「压缩与无效果不可区分」的结论，**机制解释变了**：

| 旧解释 | 新解释（有探针证据） |
| --- | --- |
| 压缩器压了，但收益被摘要成本吃掉 | **压缩器压根没触发**（预算漏算 → 阈值永不达标） |
| 结论：这个 agent 不需要压缩 | 结论：**先得让它真的跑起来，才谈得上需不需要** |

Batch D 曾观察到"压缩 +25% 灾难性失败"、Batch F/G 观察到 ±10% 上下浮动——
如果当时也没触发，那**那些数字全是采样噪声**，与压缩无关。
⚠️ 不能断言历史数据都无效（早期版本参数不同、可能触发过），但**所有历史压缩结论都必须重测**。

**教训（本轮最贵的一条）**

> **「调用了」不等于「执行了」。**
> 任何"某功能没效果"的结论，第一步不是加大 n、不是换指标，而是先证明**功能真的跑起来了**。
> 这个 bug 藏了两周，因为它长得像"一个正常工作的优化"，而不是像一个错误。

### Batch M（2026-10-26，修好估算后：**压缩第一次显出正向迹象**，同时暴露"水位"问题）

**两处修复**

1. `estimate_tokens` 从统一 `len // 4` 改为 **CJK 加权**（`count_tokens`：中文按 1 token/字，
   其余 4 字符/token）。原来对中文系统性低估 1.7 倍。
   同时把 `context.py` 里另外两处 `// 4`（无悔闸门的收益估算、tool schema 估算）统一到该函数。
2. 触发水位改为可用 `COMPRESS_THRESHOLD` 环境变量扫（默认 4000）。

**修复后的触发行为（t26 探针，单次运行）**

| | 修复前 | 修复后 |
| --- | --- | --- |
| 首次触发 | 第 21 轮 | **第 10 轮** |
| 触发次数 | 0 / 12 | **17 / 26** |
| 每次调用真实 token | 7,478（估算 3,921） | 3,588（压缩真的生效了） |

**水位扫描（t26，`max_iter=40`，各 3 次，方向性）**

| 组 | 3 次 token | 通过 | 均值 | 最差 |
| --- | --- | ---: | ---: | ---: |
| base（不压） | 108k / 364k / 81k | 2/3 | 184,375 | 363,641 |
| **cmp@4000**（每轮都压） | 131k / 117k / 78k | **3/3** | **108,608** | **130,777** |
| cmp@12000（几乎不压） | 67k / 592k / 613k | 1/3 | 424,154 | 613,240 |

**加样本确认（t26，base vs cmp@4000 各 5 次）**

| 模式 | 通过 | 均值 token | 最差 | 平均调用数 |
| --- | ---: | ---: | ---: | ---: |
| base | 3/5 | 240,311 | 384,054 | 24.6 |
| **compress@4000** | **4/5** | **111,744** | **155,377** | **23.6** |

**−53.5%**，且**调用数几乎没变**（−1.0）——说明省的是"每次调用的输入长度"，
不是"少干活"。这是第一次看到符合预期的压缩行为。

**⚠️ 但仍不能当结论（样本极弱）**
- **n=5、单任务**。配对报告里 n(任务)=1，t 值恒为 0，无法做检验。
- base 3/5 vs compress 4/5 只差一个样本，**完全无统计意义**。
- `cmp@12000` 只有 3 次且两次爆掉（592k / 613k），不能据此说"晚压更差"，只能说
  **没有证据表明晚压更好**。

**对"水位"的新认识（这是本轮真正学到的东西）**

压缩不是"要不要"的问题，是**在什么水位压**的问题：

- 太晚（12000，高于真实上下文水位）→ 几乎不触发 → 等于不压，长尾照旧；
- 太早（4000，相对 7.5k 的真实上下文）→ 每轮都压 → 本次实测反而没坏事，
  但风险明确：**摘要丢掉"已经读过/改过什么"，agent 会重读重改**。

净收益应该这样算：

```
压缩净收益 = 省下的重发成本 − 因遗忘导致的重读/返工成本
```

t26 之所以看起来赚，是因为它的快路径"读完 12 个文件就动手，不再回看"——
重读成本接近 0。**换成需要反复跨文件对照的任务（如 t23、t24），这个公式可能翻负。**
下一步必须在"需要反复回看"的任务上验证，这是唯一能判定压缩边界的方法。

### Batch N（2026-10-26 夜，**验证"遗忘成本"失败**：因为压缩压根没稳定触发）

**目的**：验证 Batch M 提出的公式 `净收益 = 省下的重发 − 因遗忘的重读`，
在"需要反复跨文件对照"的任务（t23 跨模块 / t24 契约反推）上是否会翻负。
为此把占位指标 `read_repeats` 真正实现了（`RunStats.read_paths` + `Counter` 求 sum(count-1)）。

**第一轮结果（各 3 次）——数字看着有戏**

| 任务 | base 均值 | compress 均值 | 变化 |
| --- | ---: | ---: | ---: |
| t23 | 41,252 | 32,282 | −21.7% |
| t24 | 21,649 | 24,636 | +13.8% |

`read_repeats` 全为 **0**。

**但先问了一句：压缩到底触发了没有？**

| 任务 | est 峰值 | 阈值 | 触发次数 |
| --- | ---: | ---: | --- |
| t23 | 3,800 | 4,000 | **0 / 8** |
| t24 | 3,523 | 4,000 | **0 / 6** |
| t26 | 5,932 | 4,000 | 6 / 13 |

→ **t23 / t24 的 −21.7% 和 +13.8% 全是采样噪声**，两组跑的其实是同一个东西。
`read_repeats=0` 也不能证明"压缩没造成遗忘"，只能说明"压缩没发生"。

**第二轮换 t25（长轨迹、6 个类同文件、天然需要回看）：还是不稳**

| t25 compress | token | 调用 | 触发 | est 峰值 |
| --- | ---: | ---: | --- | ---: |
| #1 | 27,673 | 8 | **0 / 8** | 3,510 |
| #2 | 79,377 | 22 | **3 / 15** | 4,405 |
| #3 | 33,083 | 9 | **0 / 9** | 3,777 |

**三次只有一次真正触发。** 峰值 3,510 / 4,405 / 3,777 —— 全部贴在阈值 4000 上下。

### 根因：阈值正好落在这个 agent 的"临界区"

26 个任务的上下文峰值集中在 **3.5k – 6k**，而阈值是 4000。
于是"压缩是否发生"本身成了一个**随机事件**：
跨过 4000 就压，差 200 就不压。

**这在实验设计上是一个致命问题：样本来自两个不同的分布（压过 / 没压过）混在一起。**
这时算出的均值差，测的不是"压缩的效果"，而是"这次有没有跨过门槛"。
医学统计里叫 **intention-to-treat 陷阱**——你统计的是"发了药"的效果，
而不是"吃了药"的效果，因为一半病人没吃药。

**推论（本轮最重要的两条）**

1. **在触发变成确定性事件之前，压缩的效果问题没有意义。**
   要么把阈值调低到"必然触发"（3000），要么把任务做长到"必然超过 8000"。
   中间地带是最坏的——既压不到，又永远有希望。
2. **停滞检测和压缩器互相冲突。**
   Batch K 的 `stall` 专门砍掉长尾轨迹（把它们定在 10 步内终止），
   而压缩恰恰只在长轨迹上才可能回本。**一个在缩短轨迹，另一个在等长轨迹。**

**这一轮没有产出压缩结论，但产出了一个方法论结论：**
> 当处理组"只有一部分真的接受了处理"时，A/B 的差值不可解释。
> 先测「处理有没有发生」，再测「处理有没有用」。
> （这是 10-23 那条"调用了 ≠ 执行了"的升级版：**触发了 ≠ 稳定触发**。）

### Batch O（2026-10-26 夜，压缩议题**定稿**：从"有没有用"改为"什么时候不该用"）

Batch M 测出 −53.5%，Batch N 又证明那个数字随时会变成噪声。继续加样本只会重复同一件事。
所以这一批不做实验，只做**决策**——把这条战线收成一个结论。

### 盈亏平衡模型（两次实验的几何解释）

```
净收益(轮数) = k × 轮数   −   C_遗忘
               └ 线性累积 ┘   └ 一次就阶跃 ┘
```

- **k（每轮省下）**：由"可压内容占比"决定。`PRESERVE_TOOLS` 保护 `ReadFile`/`EditFile`/
  `WriteFile`/`Grep`，所以文件内容永不压缩 → 可压的通常只剩 Bash 回执与对话 → **k 很小**。
- **C_遗忘（重读代价）**：一次完整调用（含工具 + 全量上下文重发）≈ 6k–8k token。
  **一次重读就吃掉 8–10 轮的节省。**

| 任务 | 量级 | 位置 | 实测 |
| --- | ---: | --- | --- |
| t23 / t24（跨模块对照） | 8–9 轮 | 蓝线未过半 | 压缩触发 0 次（峰值 3800/3523 < 4000） |
| t26（一次性勘察型） | 24 轮 | 远过台阶 | −53.5%（n=5 单任务，趋势） |
| t25（同文件反复定位） | 8–22 轮 | 贴在台阶上 | 3 次只触发 1 次 |

### 三条候选路线，为什么选"默认关"

| 路线 | 做法 | 为什么不选 |
| --- | --- | --- |
| a. 降阈值到 2000 | 短任务也必然触发 | **强迫全部任务在亏区运行**：省的少，遗忘代价不变 |
| b. 任务做到 >8000 | 长任务必然触发 | 能出结论，但代价是评测集失去干净基线、每次跑更贵；且 **`stall` 专砍长尾，压缩等长轨迹——两个机制在争同一个场景** |
| c. 闸门自适应 | 让公式自己判断 | **不可行**：`剩余轮数 × k > 摘要成本` 只能算清成本，算不清"后面会不会重读"（取决于 agent 之后的走法，事前不可知） |

> **所以压缩不是"要不要"的开关，是"什么形态的任务"的判断题。**
> 而这个判断题在本项目的任务分布（8–25 轮）里，答案多数是"不要"。

### 落地的决策

| 项 | 决定 |
| --- | --- |
| 默认值 | `compress=False`，并在 `agent.py` 注释写明这是**有意决策**而非未完成 |
| 适用形态 | 只对「一次性勘察型」（读完即动手、不回看）保留正收益可能 |
| 代码保留理由 | 其一，"文件操作轮次永不压缩"是**正确性**修复（曾因盲摘要致 +25% 灾难性失败）；其二，它是"处理未发生时 A/B 不可解释"这条方法论的载体 |
| 对外口径 | 不报百分比，只报**边界**：压缩只在"读完不回看"的长轨迹上有收益，其余场景默认关 |

### 这一批不产出数字，产出一条判据

> **当两个机制的优化方向相反时（一个要短轨迹、一个要长轨迹），不要在同一个评测集上
> 比较它们的收益，而要分别声明各自的适用区间。** 否则你永远在拿 A 的地形评价 B。

### Batch P（2026-10-26 夜，**真实 CLI 路径验证**：接线正确 + 零误报，但靶子比想象中窄）

评测脚本里能跑，不等于命令行能用。三个探针都走 `python cli.py ... --stall`。

| # | 任务 | 调用 | 耗时 | 结果 | `stall_idle_max` |
| --- | --- | ---: | ---: | --- | ---: |
| 1 | 正常任务：建 `calc.py` + pytest 并跑通 | 4 | 7.5s | done | **0** |
| 2 | 目标文件不存在（15 模块，无 `config.py`，禁新建） | 5 | 17.3s | done | **0** |
| 3 | 重构 15 个模块、抽公共基类并保持向后兼容 | 11 | 34.1s | done | **0** |

**接线正确、零误报**（探针 3 有 11 次工具步、全程读写，判据没有被"连续读不同文件"骗到）。
**但也零触发**——三次都没出现空转。

### 探针 2 的意外结论

模型找不到文件后，**主动停手并解释**：列出 15 个文件、`grep` 零命中、
并说明"为什么我不顺手新建一个 config 来假装完成"。这不是空转，这是正确行为。

> **空转的成因不是"任务难"，是"没有明确的完成判据"。**
> 当 agent 知道"报告找不到"也是合法结束时，它不会打转；
> 真正打转的是**它认为事情还没做完、但看不到全貌**（96 类那次 `41 calls / 0 改动`）。

这修正了此前的一个直觉（"需要判断的任务更容易空转"）。t26 的空转率高，
不是因为"要判断"，而是因为它的完成判据（3 真 bug 都改对）**对 agent 不透明**——
它没法确认自己改完了，只能继续找。

### 对统计困境的解释

11 次配对合并 t=−2.21、差 0.018 未过线。之前归因于"样本太小"，本轮给出了更准确的解释：

> **护栏的有效性取决于故障发生率，而空转是低频事件。**
> 分母本来就大部分是零，小样本测不出显著是**结构性结果**，不是实验设计缺陷。

推论（决定对外口径）：
1. 护栏只能用**最坏情况**和**方差**衡量，不能用平均收益——平均里掺了大量 0。
2. 想证明它有效，唯一正当路径是**提高故障发生率**（选天然会空转的任务族），
   而不是加大 n。
3. 也因此，**"护栏不误伤"比"护栏有收益"更容易验证、也更该优先报告**。

### Batch Q（2026-10-26 夜，找到失控的**真根因**：任务 prompt 给了假完成信号）

**触发点**：核对 t26 的 prompt 时发现自相矛盾的一句——

> 完成的定义：`pytest tests` 全绿，且三处算错的账在修复后能得到正确结果。

而 `pytest tests` 在 setup 之后就是 **4 passed 全绿**。
也就是说：**agent 一开局就已经"符合完成定义"了**，但任务又要求它修 3 个 bug。
它面前同时有一个"绿灯（已完成）"和一个"任务未完成"，只能靠反复确认来消解这个矛盾。

**对照实验（只改这一句话，其余完全相同，各 3 次，max_iter=40）**

| 组 | prompt | 通过 | 状态 | 调用 | token |
| --- | --- | ---: | --- | ---: | ---: |
| A（原版） | 完成 = pytest 全绿 | **0/3** | max_iter ×3 | 41 / 41 / 41 | 685,811 / 337,816 / 346,451 |
| B（改版） | 明示"绿灯是假信号，别拿它当完成信号" | **3/3** | done ×3 | 10 / 9 / 8 | 52,925 / 44,614 / 37,719 |

**A 组在带 stall 时的工具序列（决定性证据）**

```
Bash→Bash→ReadFile×12→Bash×22→终止
                      └─ 空转累积达 10 轮 ─┘
status=stalled, 26 calls, 191,069 token
```

- 前 12 次读的是**不同文件** → 判据正确识别为「有进展」，没误杀；
- 后 22 次是**重复的 Bash** → 判据正确识别为「无新信息」→ 第 10 轮终止；
- 对照不带 stall 的同配置：**41 calls / 685k token / 跑满预算**。
- **它在反复跑 `pytest` 看那盏永远绿的灯。**

→ stall 在这个靶子上精确生效：**26 vs 41 calls（−37%）、191k vs 685k token（−72%）**。

**但修好 prompt 之后，失控并没有归零**

| 配置 | 通过 | 失控次数 | 平均 token |
| --- | ---: | ---: | ---: |
| 原版 prompt | 0/3 | **3/3** | 456,693 |
| 修好 prompt | 2/3 | **1/3** | 206,448 |

那 1 次仍是 41 calls / 514,366 token——**同一个失控形态**。

> **结论修正：假完成信号是放大器，不是唯一成因。**
> 修掉它把失控率从 3/3 降到 1/3；剩下的 1/3 来自任务本身的不确定性
> （3 真 2 假的判断，有时会走偏）。**这恰好说明 stall 不是多余的**——
> 它兜的正是"根因修完仍然会漏"的那部分。

**由此得到一条可复用的任务设计规则（已写进 README）**

> **任务 prompt 里不能出现"完成 = 某命令通过"，除非该命令初始是失败的。**
> 全绿的测试比没有测试更危险：它给的是**假信号**，而 agent 会认真地按它执行。
> 要么给真信号（红灯 → 绿灯），要么明确说"这里没有可用的信号，自己判断"。

**对历史结论的影响（必须修正）**

- Batch J/K 的 t26 数据是在一个**有 prompt 缺陷**的任务上测的。
  「空转率 6/10」「最坏 −81%」这些数字的方向没错（stall 确实拦住了失控），
  但**效应量被放大了**，因为失控本身有一半是任务设计造成的。
- 修复后 t26 的基线是 2/3 通过，t26 不再能作为"稳定失败任务"引用。
- 教训与 Batch L 同构：**在修复被测量对象的设计缺陷之前，任何关于它的效应量都要打折扣。**

### Batch R（2026-10-26 夜，把 Batch Q 的规则做成**机器判据**，并立刻用它抓到 2 个新缺陷）

**动机**：Batch Q 得到的规则是"prompt 不能出现「完成 = 某命令通过」，除非该命令初始是失败的"。
但这条规则一直是**人肉 review**——靠我某天恰好盯着 prompt 才发现 t26。
人肉 review 的问题是：它只在"我怀疑某个任务"时才发生，而缺陷恰恰藏在**我不怀疑**的任务里。

**做法**（`eval/prompt_audit.py`，机器可判）：
1. 抽 prompt 里反引号包住的命令（`pytest` / `python` 前缀）；
2. `setup()` 之后**原样跑一遍**（不是推断，是真跑）；
3. `rc == 0` → 该命令开局就绿 → 若被当完成判据就是假信号；
   `rc != 0` → 合法完成判据（如 t18 的失败测试）；
   跑不起来 / no tests ran / 超时 → 不构成信号；
4. 已知例外必须写进任务 dict 的 `audit_ok` 字段，**显式登记，不靠推断放行**。

**首跑结果：26 任务里抓到 2 个此前未知的同类缺陷**

| 任务 | 假信号 | 为什么一直没暴露 | 处理 |
| --- | --- | --- | --- |
| t22 | `pytest tests` 初始 **5 passed**，prompt 写"完成后必须运行确认 5 个测试全部继续通过" | t22 在 26 任务全量评测里**稳定通过**，从没卡住过 | prompt 加声明"只能证明没弄坏，不能证明写对了" + `audit_ok` |
| t20 | `python -c "import legacy"` 初始就过 | 同上，机械式任务一次就成 | 同上 |
| t18 | 命令写在正文里、反引号外，审计一开始抓不到 | — | prompt 改成可执行形式 `pytest test_stack.py`，让审计能真跑 |

**方法论收获（比脚本本身值钱）**

1. **基线满分 ≠ 任务没问题。**
   t22 通过率 100%，所以假信号零代价；但只要哪次模型抽风向差一点卡住，
   它就会撞上和 t26 完全一样的死循环。**假信号是地雷，不是现症。**
   之前所有"任务质量"检查（selftest / verify_strictness）都只测**判卷**，
   没有一条测**给 agent 的信息是否自洽**——这是评测体系里一个整块的盲区。
2. **规则的价值取决于它能不能被机器执行。**
   Batch Q 的规则写得再对，只要还是靠我"想起来查"，它就不会被系统性执行。
   落地成脚本之后，第一次跑就吐出 2 个我自己写的、review 过很多遍的任务。
3. **本次先做的两次审计都是错的，才收敛到对的。**
   第一版用"有完成措辞但没有命令"做启发式 → 11 个任务误报（"完成"太常见）；
   第二版用 `default` venv 跑 → 环境里没有 pytest，`pytest tests` 报 ModuleNotFoundError，
   把 t22 误判成"初始失败"。**换到项目 `.venv` 才看到真正的 5 passed。**
   → 审计脚本自己也踩了"没确认处理真发生"的老坑，只是这次踩在工具上。

**验证**：`pytest tests -q` → **37 passed**（新增 5 条审计回归，防止审计自己失效）；
`prompt_audit.py` 全量 → 零假信号，2 个例外显式登记；
`selftest_tasks.py` 全量 → 26 任务仍全部可解（改 prompt 没破坏任务）。

### Batch S（2026-10-27 夜，Phase 2 第一块：Skill 路由 + 第一个"答案不在仓库里"的任务）

**为什么换方向**

前面 Batch H–R 都在优化「已有信息怎么用」（规划 / 压缩 / 停滞检测）。三条线全部收敛到同一个天花板：

> **26 个任务的答案都在仓库里。** 再会规划、再省上下文，也变不出新信息。

所以这一批换问题：**Agent 缺的信息，如果不在仓库里呢？**

**做了什么**

1. `skill_router.py`：两阶段检索（BM25 粗召回 → tag 精确准入 + 规则精排），
   只把命中的 description 注入 system prompt，正文要 agent 主动 `LoadSkill` 拉。
2. `skills/` 下 3 篇真实技能文档（rates-api / pytest-style / refactor-safety），
   **放在 workdir 之外**——agent 只能通过工具访问，`Grep` 搜不到，这才有干净对照。
3. `eval/tasks/t27_external_api_contract.py`：第一个"答案不在仓库里"的任务
   （外部汇率 API 的限频 / 重试规则 / 时间戳单位）。
4. 接线：`CodingAgent(skills=True)`、`--skills`、`repeat.py --modes base skill`。

**t27 的判卷为什么可信（双向校验都做了）**

- `selftest_tasks.py t27` → 初始失败 / 参考解通过（任务可解）
- `verify_strictness.py t27` → 4 个**"通用最佳实践"错误解全部被拦**：
  TTL=60 / 全部异常都重试 / ts 按本地时区 / ts 当毫秒
  这四条正好是"不给 skill 时 agent 最可能写出的答案"，所以拦住它们 = 任务有区分度。

**预注册预测（结果出来前写下，防止事后解释）**

| 模式 | 预测 | 理由 |
| --- | --- | --- |
| base（无 skill） | **0/3** | 会写 TTL=60（"更实时"）、重试所有异常（"更健壮"）、`fromtimestamp` 不带 tz。三条都是通用做法，本地测试全绿，猜错不报错 |
| skill（有路由） | **2/3 或 3/3** | 摘要能召回 rates-api；但即使读了全文，仍可能漏掉"必须带 tz=UTC"这一条——那是文档里的括号说明 |

若 base 出现非 0，说明这题的"知识依赖"不够硬（它靠猜蒙对了），要重新设计。

**过程中撞到的两个真问题（比实验结果本身更有价值）**

第一次跑 t27 时，base 模式 25 轮跑满、单任务耗时 3.5 分钟、`rates.py` 一个字没改。
打开轨迹才发现两件事：

1. **Bash 逃出了沙箱。** prompt 让 agent「去查技能文档」，base 模式下它没有检索工具，
   于是自己执行 `find / -name SKILL.md` —— **真的扫到了 `C:\Users\王\.claude\plugins`**，
   读到了用户主目录里的文件，其中一条命令还跑满 30 秒超时。
   `cwd=workdir` 只限制「默认起点」，不限制「能去哪」：`cd /`、`find /`、绝对路径都能走出去。
   → 已加 `_ESCAPE_PATTERNS`（`tools.py`）拦截高置信度逃逸写法，
   配 6 条单测，**并专门验证"正常命令一个都不能误伤"**——误伤会让 agent 以为工具坏了，
   改用更绕的写法继续试，比不拦更糟。
   > 这条也修正了 README 里"Bash 不是真沙箱"那句话的分量：
   > 它不是"理论上不严谨"，是**实测已经走出去过**。

2. **任务 prompt 写坏了（和 Batch Q 同一类错误，只是方向相反）。**
   Batch Q 是"给了假完成信号"；这次是"给了一个它没有能力执行的指令"——
   让 base 模式"去查文档"，它没有检索工具，只能全盘搜索。
   这会让 base 组的表现被"找文件"污染，而不是被"不知道知识"污染，**对照就废了**。
   → prompt 改为「不要试图在文件系统里搜索；如果你手上有检索技能文档的工具，先查一下；
   没有就按你认为最稳妥的方式判断」。base 与 skill 共用同一段 prompt，
   差别只在 skill 模式多注入了技能摘要 + `LoadSkill` 工具。

> **教训**：给 agent 的指令必须和它**实际拥有的工具**匹配。
> 让它做一件它没有工具可做的事，它不会说"我做不到"，而是会找一条更糟的路去做。

**结果（t27，max_iter=15，各 3 次）**

| 模式 | 通过 | token（3 次） | 均值 | 调用数 | 技能命中 / 加载 |
| --- | ---: | --- | ---: | ---: | --- |
| base | **0/3** | 58,094 / 57,464 / 45,510 | 53,689 | 12.3 | — |
| skill | **3/3** | 42,494 / 51,765 / 46,672 | **46,977** | 10.0 | rates-api（3/3 都读了全文） |

- 通过率：**0/3 → 3/3**，符号一致性 100%（6 次运行里 3 次稳定败、3 次稳定过）。
- 成本：skill **反而低 12.5%**（−6,712 token）、调用少 2.3 次。
  不是因为"少干活"，而是因为 base 在**错误路径上多绕**：写错 TTL → 反复验证/怀疑 → 更多轮。
- 失败归类：base `wrong_behavior ×3`（行为写错）；skill `passed_with_retry ×3`。

**必须打折扣的地方（照实写）**

> **n = 1 个任务**，配对 t 检验退化成 df=0、t=0.00。
> 报告脚本自己就警告「任何百分比都不可写进报告」，我认这个警告。

所以对外只能这么说，不能更狠：

> "在**一个**'答案不在仓库里'的任务上，base 3/3 稳定失败、skill 3/3 稳定通过。
> 这是**存在性证明**（这个机制能解决这类任务），不是**效应量估计**（能省多少 token）。
> 效应量需要 ≥10 个这类任务，目前只有 1 个。"

**为什么这个结果比"省 token"更有意义**

Skill 的价值不是"更便宜"，是"**把不可能变成可能**"。
前面 Plan / 压缩 / 停滞三个机制，报的全是成本数字（−0.9%、−29.8%、−53.5%），
因为通过率早就锁死在 100%，它们**没有能力改变对错**。
t27 是第一个能改变对错的机制——虽然样本只有 1 个任务。

**回归验证：skill 会不会损害"本来就会做"的任务**

只测 t27（新任务）不够——必须确认它不会把原来能过的任务搞坏。
选 t22（新增功能不回归）和 t24（隐式契约）各跑 3 次：

| 任务 | base 通过 | skill 通过 | base token | skill token | Δ |
| --- | ---: | ---: | ---: | ---: | ---: |
| t22 | 3/3 | 3/3 | 29,087 | 25,028 | **−4,059（−14%）** |
| t24 | 3/3 | 3/3 | 20,921 | 29,407 | **+8,486（+41%）** |

- **通过率零损害**（两边都 100%，6 次全过）。
- 成本均值 **+8.9%，但符号不一致**（一省一增），配对 t=0.35 (df=1) —— **纯噪声，不可引用**。
  单任务 token 波动本来就有 ±40%（这是 Batch I 就记过的老问题）。

**为什么 t24 会 +41%：召回准了，但召回了"不需要"的**

t24 的 prompt 里提到 `pytest`，于是 tag 命中 `pytest-style`，agent 多花一轮读全文——
但 t24 要的是**实现两个函数**，pytest 只是验证手段，不是它缺的知识。

> 这说明当前检索有一个明确缺陷：**区分不了「任务提到 X」和「任务需要 X 的知识」**。
> tag 是词面匹配，而"提到"是手段、"需要"是需求。
> 改进方向（未做）：命中后要求 `when_to_use` 也匹配，或用一次廉价 LLM rerank。
> **本轮不改**——改检索要重跑全部对照，不能和"验证机制是否生效"混在一轮里
> （这是 Batch N 的 ITT 陷阱给的教训：一次只动一个变量）。

**这一轮真正立住的三句话**

1. **Skill 能改变对错**（t27：0/3 → 3/3），这是前面 Plan / 压缩 / 停滞都做不到的
   ——因为它们只优化"信息怎么用"，而 26 个任务的答案本来就在仓库里。
2. **它不损害正常任务**（t22/t24 通过率零变化），但会**白花约 9% token**
   ——因为召回准≠召回必要。所以默认关、按需开，而不是常开。
3. **n 太小，只能讲存在性**。效应量要 ≥10 个"答案不在仓库里"的任务，
   目前只有 1 个（t27）。下一步是造同类任务族，不是继续调检索参数。


**t24 那 +41% 的归因（查过才写的，不是推断）**

先排除"多干活"：skill 组产物 137 / 137 / 140 行，base 组 138 行 —— **代码量一样**。

算账：

```
skill 全文 ≈ 1,500 token
t24 skill 组平均 6.67 轮（base 5.67）
一次 LoadSkill 的真实成本 = 1500 × 剩余轮数 ≈ 1500 × 6 ≈ 9,000
实测增量                                  = 8,486
```

**对上了。** 一次 `LoadSkill` 不是"读一次 1,500 token"，是
**"读一次 + 之后每一轮都随历史重发"**——和上下文压缩里的"重发成本"是同一个机制。

> 这就是 Skill 的成本结构，和压缩那条公式完全同构：
> ```
> LoadSkill 净收益 = 用上它的轮数 × 每轮省下的返工  −  读完之后的轮数 × 1500
> ```
> 用不上时（t24），右边那项照付，左边是 0 ——**读得越早、轮数越多，亏得越多**。

**t24 和"第二个问题"是同一类错误的两个层面，但错法相反**

| | 第二个问题（t27 第一次跑） | t24 的 +41% |
| --- | --- | --- |
| 层面 | **能力层**：给了一个它没工具执行的指令 | **需求层**：给了一份它不需要的知识 |
| 表现 | base 去 `find /` 全盘搜索，8 轮烧光 | 读了 `pytest-style`，然后按原样写完，规范一条没用上 |
| 后果 | **破坏对照**（base 输在找文件，不是输在不知道） | 只是白花钱，对错不受影响 |
| 修法 | 改 prompt，让指令匹配工具能力 | 不改检索（要单独一轮），先默认关 |

一个是"给了做不到的事"，一个是"给了用不上的东西"。
共同点只有一条：**都在替 agent 做判断，而判断错了**。


**修正上表：t24 和「第二个问题」不是同一个原因（2026-10-27 晚，老王指出）**

我一开始写的"共同点是都在替 agent 做判断"是错的，把两种截然不同的失败糊成了一个。
正确的分法是**按"有没有交付"切**：

| 失败类型 | 有交付？ | 例子 | 是谁的锅 | 该看什么指标 |
| --- | --- | --- | --- | --- |
| **零交付** | ❌ 一个字没改 | t27 第一次跑：`find /` 烧 8 轮，零改动 | **我的**（prompt/任务缺陷） | 改动行数 == 0 |
| **交付但错** | ✅ 改了，改错 | t27 修好 prompt 后的 base：TTL=60 | agent 的知识/判断 | verify 的失败原因 |
| **判断多余** | ✅ 改了，且对 | t24：多读了文档，结果没错 | 检索策略 | 白花的 token |

- 前两类在**通过率上完全一样（都是 0）**，混在一起就会把"我的 bug"算成"它不行"。
- 第三类不影响对错，只是成本。

**如果不做这次诊断，会得出什么错误结论**

直接跑 base vs skill 对照，看到 base 0/3，自然会写"skill 让 agent 学会了查知识"。
但 base 的 0/3 里，有相当一部分是**输在没法开始**（prompt 让它查文档，它没工具，只能全盘搜），
不是输在"不知道限频是 60 次/小时"。**这样的对照测的不是知识，是我的 bug。**

修好 prompt 之后 base 才变成干净的 `wrong_behavior`（写了代码、TTL 写短），这才是有效对照。

**已落成机器判据**（不然下次还会混）

- `RunStats.writes_ok`：成功的 WriteFile + EditFile 次数
- `build_metrics` 加 `delivered`（bool）与 `no_delivery`（fail_reason 的一个值）：
  失败且 `writes_ok == 0` → 归为 `no_delivery`，**覆盖掉** `max_iter` / `wrong_behavior`
- `tests/test_delivery_attribution.py` 3 条：零改动必须归 no_delivery；改过就保留原归因；通过的不受影响

> 这个字段的价值不在于多一个指标，在于它让"**我的任务坏了**"和"**agent 不行**"
> 在报表里长得不一样。之前它们在报表里长得一模一样。


**t27 解决了"通过率锁死 100%"吗？—— 解决了一半，而且这一半有陷阱**

| 问题 | 是否解决 | 说明 |
| --- | --- | --- |
| 通过率是死值（26/26 = 100%） | ✅ **解决了** | 加 t27 后 base 变成 26/27 = 96.3%，通过率重新能动了 |
| 通过率能度量 **Plan / 压缩 / 停滞** 吗 | ❌ **没有** | 这三个机制都改不了 t27 的对错——它们不缺知识，缺的是"怎么用信息"。t27 对它们仍是常量 |
| 通过率能度量 **skill 的实现质量**吗 | ❌ **没有** | 见下 |

**陷阱：t27 是开关，不是刻度尺**

t27 的区分是**确定性**的：不给知识必败、给知识必过（0/3 vs 3/3）。
这能回答"有没有这个功能"，**不能回答"这个功能做得好不好"**：

- 如果我去改进检索精度（解决 t24 那种"召回了但不需要"），
  t27 通过率还是 3/3，**看不出任何改进**。
- 要度量"质量"，需要的是**难度连续**的任务——不同质量的实现落在不同通过率上。
  t27 只有 0 和 1 两个取值，没有中间态。

**还有一个必须自己先说的问题：构造效度**

t27 是**我为了验证 skill 特意造的任务**（先有 feature，再有靶子）。
那么"skill 在 t27 上 3/3"能证明什么？

- ✅ 能证明：**它确实在"知识不在仓库里"这一类问题上起作用**（存在性）
- ❌ 不能证明：**这类问题在真实任务里占多大比例**（我挑选了场景）

这是我选择偏差，不是测量结果。要削弱它，唯一的办法是
**先造任务族、后看有多少 skill 能命中**——而不是反过来。
→ 所以下一步是造 10 个同类任务，**且其中一部分要故意造得让现有 3 篇 skill 都盖不住**
（否则又是一次"我造题给我自己的答案"）。


**「skill 覆盖不到时，为什么不改 skill？」—— 评测期必须冻结技能库**

这是我给自己定的纪律，理由是把两件事分开了：

| 场景 | 该不该补 skill | 为什么 |
| --- | --- | --- |
| **评测中**看到某任务失败 | ❌ **不改** | 改了就是"对着答案改技能库"= 测试集泄漏进训练集。测出来的是"我补得多快"，不是"agent 多能干" |
| **生产/日常**发现知识缺口 | ✅ 该补 | 这是知识沉淀的正常流程，和度量无关 |

同一条纪律之前用过两次：拒绝"跑到达标为止"地加大 n（Batch K）、拒绝"为假设找旁证"（48 类误判）。
**度量阶段只允许改被测对象和尺子，不允许改答案。**

**"覆盖不到"要先分清三种，只有一种该补**

1. **缺知识**（外部契约存在但没人写下来）→ 该补，但在**评测之后**补，并重测
2. **没检索到**（库里有，召回失败）→ 改检索策略，不是补库
3. **不该有**（本该从代码读出来 / 该由 agent 自己判断）→ **永远不补**，
   补了就是把"读代码"这项能力废掉，让 skill 变成答案本

第 3 类是关键：如果所有任务都能被 skill 解决，那要么技能库膨胀成了"预先写好所有答案"，
要么任务是我按 skill 反向定制的。**一个覆盖 100% 的技能库是可疑的**，
真实工程里团队知识永远不完整。

**所以下一步造 10 个任务时，要故意留 2–3 个"现有 3 篇 skill 都盖不住"的，测的不是通过率，是校准：**

> 覆盖不到时，agent 会说"我不确定，按最保守的方式做"，还是自信地猜？
>
> 后者更危险——它会把"我不知道"伪装成"我知道"，而这类错误静默失败。
> 这才是 t27 这个方向真正值钱的副产品：**能测"知不知道自己不知道"**。

### Batch T（2026-10-28 夜，任务族第 2–4 个：t28/t29/t30，以及一次"我的题写坏了"的自我纠正）

**目标**：昨天只有 t27 一个"答案不在仓库里"的任务，n=1 说不出效应量。
今晚造 3 个，并且**故意让 t30 没有任何可用 skill**，用来测"知不知道自己不知道"。

| 任务 | 缺的知识 | 有无 skill |
| --- | --- | --- |
| t28 消息队列契约 | prefetch 上限 / ack 超时余量 / 死信规则 | ✅ messaging-contract |

| t30 增量同步校准 | 源系统行为（游标/重复/删除/时区）**故意不给** | ❌ 无 |

三个都做了双向校验：`selftest` 初始必败+参考解通过；`verify_strictness` 把
**"通用做法"错误解全部拦住**（t28 四个、t29 三个）。

**🔴 第一次跑就发现 t28 是我的题写坏了（base 1/1 通过）**

base 用 9 次调用就通过了——它猜 `prefetch=10`、`ack=处理耗时+30`。
原因不是它懂，而是**我在 prompt 里给的三个症状各自直接指向一个修法**：

| 我写的症状 | 它推出的修法 |
| --- | --- |
| "broker 直接断开了连接" | 要限流 → 设个保守 prefetch |
| "一条消息被两个消费者同时处理" | ack 超时不够 → 加余量 |
| "毒消息无限循环" | 不能 requeue → `reject(requeue=False)` |

> **教训：症状描述 ≠ 知识缺口。**
> 症状足够具体时，agent 能**反推**出正确做法——那这题考的是推理，不是知识。
> 要让它真的依赖外部知识，**关键参数必须是"猜不到的数字"**，而不是"能推理出的方向"。

修正：prefetch 上限 10 → **7**（每连接 7 个槽位，无直觉可推），
ack 余量 ×1.5 → **×2.5**（broker 重投判定有内部延迟）。
方向仍可推理（要限流、要留余量），但**数值只能查文档**。

修正后变异测试也跟着变了，而且新变异更有说服力：

| 变异 | 含义 |
| --- | --- |
| `prefetch=10` | **最"合理"的猜测值**（base 真的猜了它）→ 被拦 |
| ack 只留 1.5 倍余量 | 通用做法 → 被拦 |
| 失败 `requeue=True` | "重试啊"的直觉 → 被拦 |
| 不分成败一律 ack | 失败消息静默丢失 → 被拦 |

**t29 第一次跑：零交付（不是知识错）**

base 16 次调用、71k token、`orders.py` **一个字没改**——归因是 `no_delivery`。

找不到也不动手。已在 prompt 里补一句「**规范查不到不是停工的理由**」。

### Batch U（2026-10-28 夜，t31 重试预算 / t32 导出编码 —— 其中两个必须承认的失败）

**目标**：Batch T 之后任务族 = 4（t27–t30），离"能跑配对 t 检验"还远。
今晚再造 2 个，同时验证一个问题：**上一批的成功方法能不能复制？**

| 任务 | 缺的知识 | 结果 |
| --- | --- | --- |
| t31 重试预算 | 次数 3 / 退避 0.5·2^n 不封顶 / 422 不重试 / Retry-After 60s 上限 | ✅ 成立 |
| t32 导出字符集 | CSV 交付给 Excel 时的编码与换行 | ❌ **不成立**（base 5/5 过） |

#### t31：成立，但我的判卷先冤枉了它一次

| 模式 | 通过 | 说明 |
| --- | ---: | --- |
| base | **0 / 3** | 三次全部 `wrong_behavior`，失败原因一致：**重试 4 次**（它写 `range(1, 5)` / 5 次尝试减一） |
| skill | **3 / 3** | 读到 `retry-budget` 后六项检查全过（其中 1 次还额外读了 `rates-api`，多花 10k token） |

**🔴 第一次跑 skill 模式是 0/1，我先怀疑了 agent，实际是我判错了**

产物是完全正确的：`MAX_ATTEMPTS = 3`、`0.5 * 2 ** (attempt - 1)`、422 不重试、Retry-After 优先。
失败的检查是「退避 0.5/1.0 → 实际记录到 `[]`」。原因：

```python
def _push_one(record, sleep=time.sleep):   # 默认参数在【定义时】绑定
    ...
```

我的判法是把 `time.sleep` 重新赋值为一个记录器。但默认参数在函数定义那一刻
就把**原来的** `time.sleep` 绑走了，之后再改模块属性无效 —— 它**真的 sleep 了**，
只是走了一条我监听的路径之外的路径。

> **教训：判卷只认"我想到的那一种写法"，就是在惩罚更规范的写法。**
> 参数化注入时钟是可测试性的最佳实践，反而被判失败。

修法不是"接受它的写法"，而是**把假时钟挂到所有可能路径**：
① 模块属性 `time.sleep`；② `sys.modules["time"]` 换成幽灵模块（覆盖 `import time` 后调用的）；
③ 三者共用一个记录器。修完重测：agent 产物过、参考解过、5 个变异全部仍被拦。

#### t32：不成立 —— 这题的知识其实在模型里

base **5 / 5 全部通过**（这题被反复修了 4 轮，见下），失败经验比成功经验重要：

| 轮次 | 我改了什么 | base 结果 |
| --- | --- | ---: |
| 1 | 初版（`_TESTS` 里写了 `encoding="utf-8-sig"`） | 2/2 过 |
| 2 | 删掉测试里的编码名 | 3/3 过 |
| 3 | 清掉 verify 返回语里的 `BOM` 字样 | 1/1 过 |
| 4 | 去掉 prompt 里的"Excel"字样，改成"业务方直接双击打开" | 1/1 过 |

> "编码必须是 UTF-8 with BOM（utf-8-sig）：Excel 双击打开 CSV 时，没有 BOM 会按本地 ANSI/GBK 解码"

**我从没告诉它 `utf-8-sig`，它靠"业务方双击打开文件"这句话就推出来了。**

> **这是 t28 教训的升级版：不是"症状描述 → 反推修法"，而是"领域名词 → 反推领域常识"。**
> 只要 prompt 里出现"业务方 / 双击 / 中文报表"这类词，Windows 下 CSV 要 BOM + CRLF
> 就是模型的先验知识，根本不需要查文档。
>

> **某个对端 / 某个 broker / 某家公司自己定的具体数字或规矩**，
> 而不是任何有经验工程师都该知道的通用做法。判断标准一句话——
> **"这条约定换个公司还成立吗？"** 成立 = 不该进这个任务族。

t32 保留在仓库里，但**标为不具区分度、不进统计**（同时保留了它的

### Batch V（2026-10-29 夜，t33 SLA 超时预算 —— 第一个"约定与直觉相反"的题）

**目标**：Batch U 的教训是"领域名词会让模型推出通用做法"。这题的解法是反向利用它：
**让约定和直觉完全相反**，那么"用先验知识推理"必然推错，只能查文档。

#### 题目设计：四条反直觉的平台规定

| 项 | 直觉会怎么猜 | 平台规定 | 为什么反直觉 |
| --- | --- | --- | --- |
| 预算 P0/P1/P2 | P0 最长 | **800 / 2500 / 8000** | P0 面向前台，宁可快速失败也不让用户等 |
| 重试次数 | 越重要越多 | **0 / 1 / 2** | P0 重试会让等待翻倍 |
| 未知等级 | 给最宽松的 P2 | **P1** | 中间档误判成本最低 |
| 降级阈值 | 80% / 90% | **70%** | 剩下 30% 要留给降级路径本身 |

#### 结果

| 模式 | 通过 | token 均值 | 说明 |
| --- | ---: | ---: | --- |
| base | **0 / 3** | 29,342 | 三次**失败原因完全一致**（符合验收标准） |
| skill | **3 / 3** | 29,227 | 三次都读到了 `sla-timeout-policy`，数值全对 |

base 三次都栽在同一条：`P0 预算应为 800ms，实际 2000`。

#### ⭐ 这次失败的信息量比之前几题都大

看了 base 的产物，它**四条全错，而且错的方向完全一致**：

```python
#: 假设：P0 最宽松（用户可感知的核心链路，允许更长的端到端等待），
#: P1 居中，P2 最紧（后台/可降级链路，尽快失败）。
    "P0": 2000, "P1": 1000, "P2": 500,
#: 假设：等级越高越值得重试；P2 不重试，直接走降级。
    "P0": 2, "P1": 1, "P2": 0,
FALLBACK_LEVEL = "P2"
DEGRADE_RATIO = 0.8
```

**它的推理完全自洽**（"最重要的链路当然要给最多时间、最多重试机会"），
只是这家公司的规定正好反过来。这不是能力问题，是**领域假设错了**——
而这恰好是"必须查文档"的核心特征。

> **反过来看：如果我把 P0 设成 8000、P2 设成 800（顺着直觉），
> base 大概率会一次通过，这题就白造了。**
> **所以"反直觉"本身是保证"猜不到"的一种可复制手段**，不只是巧合。

#### ⭐ 第二个发现：知道自己在猜 ≠ 会去查

它自己写了：

```python
# TODO(平台组): 用 SLA 文档中的规定值替换 BUDGET_MS / MAX_RETRIES /
# FALLBACK_LEVEL / DEGRADE_RATIO。当前数值为占位假设，未经确认。
```

**它明确知道这些数字是猜的，还是交了唯一一份答案。**

这是 t30（校准）的延伸，而且比 t30 更尖锐：t30 测的是"会不会写 `UNCERTAIN.md`
承认在猜"，这题说明**就算承认了，它也不会因此去找答案**——
承认不确定和消除不确定之间，没有自动的因果。

#### 判卷（5 个变异全部拦住）

| 变异 | 含义 |
| --- | --- |
| P0 给 30 秒 | "最重要所以等最久"的直觉 |
| 80% 才降级 | 最常见的阈值 |
| 50% 就降级 | 过度保守，正常请求被误降级 |
| P0 也重试 | "重要的更该重试"的直觉 |
| 未知等级给 P2 | "不知道就宽松点"的直觉 |

注意第 1 个和第 4 个两个**同时**覆盖了两个方向的反直觉点，
避免"只改一处就全错"被一次抓住（否则判卷只需要一个断言就能过）。

#### 累计（t27/t28/t29/t31/t33 五题，各 2–3 次）

| 模式 | 通过 | 通过率 |
| --- | ---: | ---: |
| base | **0 / 13** | 0% |
| skill | **12 / 13** | 92% |

仍然 **n=5 任务**，配对 t 检验要 ≥10 个任务级样本，**只能讲存在性**。
README 里的"4 个任务"已同步改为 5 个。

#### 检索精度（顺手验的）

新 skill 加入后重新检查召回：
- t33 → 只有 `sla-timeout-policy`（13.9），**没有**误召 `retry-budget`（虽然都涉及重试）
- t27/t31/t22/t24 的召回与加入前完全一致（无新增误召）

### Batch W（2026-10-29 夜，t34 灰度门禁 —— 反直觉从"参数"升级到"判据"）

**目标**：t33 证明了"参数与直觉相反"有效。这题试一个更强的版本：
**不是数字反直觉，而是"该看哪个数"反直觉**。

#### 题目设计：五条反直觉的判定规矩

| 项 | 直觉 | 规定 |
| --- | --- | --- |
| 劣化怎么算 | 看 canary 错误率绝对值（>1% 就动） | 看**两组之差**，阈值 0.8 个百分点 |
| 样本少怎么办 | 更谨慎 → 更容易回滚 | 样本 < **500** 就**不判**，continue |
| 劣化的默认反应 | 立刻 rollback | 先 **hold**（停量、保留现场） |
| 什么时候才回滚 | 劣化就回滚 | 燃烧率 > **3.5** 才回滚 |
| 几次 hold 升级 | 3 次更稳妥 | **2 次** |

#### 结果

| 模式 | 通过 | token 区间 | 备注 |
| --- | ---: | ---: | --- |
| base | **0 / 6** | 27k–141k | 5 次有交付（全错在同一条）+ **1 次零交付** |
| skill | **3 / 3** | 20k–51k | 三次都读到了 `canary-gate-policy` |

> base 跑了 6 次不是凑数：首轮 3 次里出现 1 次零交付（141k token、`gate.py` 一个字没改），
> 按纪律先分「有交付 / 没交付」，再补跑 3 次确认。补跑 3 次全部有交付，
> 且**失败原因与首轮那 2 次完全一致**。

#### ⭐ 这题抓到的错误类型，比前几题都"专业"

5 次有交付的 base，全部栽在**同一条**：

```
baseline 2.0% → canary 2.5% 只差 0.5 个百分点，未达劣化阈值，应为 continue，实际 'rollback'
```

它用的是 `canary_err > 1%` 这种**绝对值判据**。这不是小白错误——
"错误率超过 1% 就该回滚"听起来非常像一条正经的 SLO 规则，
而且**在多数公司里就是对的**。它错的地方是：这家公司的基线上限已经在大促期间波动到 2%。

> **这类错误比"不知道 prefetch 是 7"危险得多。**
> 不知道就会去查；**用一条听起来对、在别处也对的规则去替代真实规则，它自己不会觉得有问题。**

反过来说，这也说明这题的设计方向是对的：
**反直觉不只可以体现在"数值"上，更有效的做法是体现在"该看哪个量"上**。
数值反直觉 → 它会猜错；判据反直觉 → 它会**自信地猜错**。

#### 判卷（5 个变异全部拦住）

| 变异 | 含义 |
| --- | --- |
| 看 canary 绝对值 | 最常见、最像专业做法的错误 |
| 不看样本量 | 300 个样本也敢判 |
| 一劣化就回滚 | 没有 hold 档，现场全丢 |
| 连续 3 次才回滚 | "更稳妥"的直觉 |
| 燃烧率阈值 1.5 | 太敏感，正常波动就被回滚 |

第 5 个变异是特意加的：**往"更严格"的方向偏也是错的**。
只测"判得太松"会让判卷偏向一边，测不出"过度保守"这种同样会杀死正常发布的错误。

#### 累计（6 题，各 2–6 次）

| 任务 | base | skill |
| --- | ---: | ---: |
| t27 外部 API 契约 | 0/3 | 3/3 |
| t28 消息队列契约 | 0/2 | 2/2 |
| t29 日志规范 | 0/2 | 1/2 |
| t31 重试预算 | 0/3 | 3/3 |
| t33 SLA 超时预算 | 0/3 | 3/3 |
| t34 灰度门禁 | **0/6** | **3/3** |
| **合计** | **0 / 19** | **15 / 16** |

6 个任务了。配对 t 检验要 ≥10 个任务级样本，**还差 4 个**。
（skill 侧 16 次 vs base 侧 19 次，因为 t34 为排查零交付多跑了一轮，不影响"0/19 全失败"这个事实。）

#### 一个未解释的现象（记下来，不解释）

首轮那次零交付：20 轮用尽、141k token、`gate.py` 一个字符没改。
同一 prompt 后续 5 次都在 27k–57k 内完成。

- 不是 prompt 问题（同 prompt 反复成功）；
- 不是任务太难（补跑 3 次全部有交付）；
- 与 t26 那次"假完成信号导致空转"不同——这题 prompt 里没有任何"完成 = 某命令通过"的表述。

> **可能和 t25/t26 是同一类：模型偶发进入"先彻底调研再动手"的模式，把预算烧在读取上。**
> 但这只是假设，**单次现象验证不了**。要验证得重复几十次统计发生率，成本不划算。

### Batch X（2026-10-29 夜，t35 埋点校验 —— 一条通过，但要如实说它只靠一条检查点）

### Batch Y（2026-11-02 夜）prompt 形态对照实验 —— 假设被证伪

**背景**：t34/t35 出现 3 次零交付（12 次里），全部伴随 130k token、20–21 轮、`writes_ok=0`。
当时的假设：

> prompt 把规矩写成 3–4 个**并列疑问句**（"哪些必填 / 异常值怎么办 / 未知字段怎么办 / 多久算重复"），
> 模型把它当成"逐个查证的清单"，把轮数烧在读取上 → 零交付。
> 支持这个假设的旁证是 t33 的 prompt 是"一串数字"，一次零交付都没有。

#### 设计：只改这一句，其余逐字相同

| 组 | 那一句 |
| --- | --- |
| **A**（原版） | 「**数据平台的规矩**：哪些字段是必填的、值里出现异常内容时该丢弃还是清洗、遇到没见过的字段该怎么办、多久之内的重复上报要拦下来。」 |
| **B**（单句） | 「**数据平台的规矩**不在代码里、不在注释里，仓库里搜不到。」 |

- 任务、判卷、skill 全部不动；A 版字符串与原 `TASK["prompt"]` **逐字相等**（做了断言校验）。
- 各 6 次 base，串行跑（避免并发抢限流污染 `infra` 判读）。
- 脚手架：`eval/exp_prompt_form.py`。

#### 结果

| 指标 | A（并列条目） | B（单句） |
| --- | ---: | ---: |
| 零交付 | **1 / 6** | **0 / 6** |
| 通过 | 0 / 6 | 0 / 6 |
| token 均值 ± sd | **75,550 ± 29,208** | **49,460 ± 11,217** |
| token 范围 | 47k – 130k | 38k – 64k |

**token 差异**：Welch t = **2.04**，df = 6.4，双尾 **p ≈ 0.08** → **未达显著**。
去掉 A 组那个 130k 离群值后，均值 64,554，差异降到 15k（30%）。

#### 结论：假设未获支持

1. **零交付 1/6 vs 0/6 无法区分**。1 次的差异在这个样本量下没有任何信息量。
   → **不能据此改 prompt 写法**。之前那个"并列条目导致零交付"的解释，撤回。
2. **两组通过率都是 0/6，且都错在同一条**（含中文整条丢）。
   → prompt 形态不影响"能不能答对"，影响面只在过程层。
3. token 方向一致（A 更贵）但**未达显著**，只能记为"待观察的趋势"。

> **⭐ 又一次踩了同一个坑：把"看起来明显"当成"显著"。**
> 我刚算出 75,550 vs 49,460 时，第一反应是"A 组明显更贵，差 53%"。
> 但 sd 是 29k，t 只有 2.04，p≈0.08——**这个差异在 n=6 下和噪声分不开**。
> 和 10-26 那次"压缩省 22%"是同一类错误：**先看到两组均值差得大，再去找解释**。
> 记在这里，下次先算 t 再说"明显"。

#### 零交付仍然是未解现象（口径修正）

实验排除了一种解释，但没有找到新的。目前的事实是：

| 任务 | 零交付 | 那几次的形态 |
| --- | ---: | --- |
| t33 | 0 / 3 | — |
| t34 | 1 / 6 | 141k / 20 轮 / 0 改动 |
| t35 | 3 / 12 | 129k、130k、143k / 20–21 轮 / 0 改动 |

**形态高度一致**：都是"读满 20 轮 → 停"，不是"读几个文件后主动放弃"。
更像固定的探索模式被触发，而不是 prompt 措辞问题。

**口径修正（重要）**：以后报 base 通过率时，分母要写成**有交付的运行数**：

> 旧：`base 0 / 25`
> 新：`base 有交付 22 次全部失败，另有 3 次零交付（不计入通过率，单独报告）`

#### 三、🔴 找到的 bug：所有两字中文 tag 永久失效

`skill_router._tag_hits` 里的匹配门槛写的是：

```python
if t in task_low and len(t) >= 3:   # ← 英文视角
```

`"限流"` / `"配额"` / `"租户"` / `"网关"` / `"重试"` **全是 2 个字符** → 一个都匹配不上。

- 前面 7 个 skill 之所以能召回，全靠它们的**英文 tag 恰好命中**
  （`prefetch` / `sla` / `canary` / `tracking` / `csv` / `retry`）——**是运气，不是设计**。
- `rate-limit-policy` 唯一的英文 tag 是带空格的 `rate limit`，而任务里写的是 `ratelimit/`
  → **没有任何 tag 命中 → 完全不召回**。
- 表现是"skill 模式 0/3，且比 base 还贵"——看起来像"这篇 skill 没用"，
  实际是路由器**根本没把文档递给它**。

修法：门槛按字符集分开。

```python
def _min_tag_len(tag: str) -> int:
    """中文 2 字符就有区分度（限流/配额/退避），英文 2 字符几乎没有（re/id/to）。"""
    return 2 if any("\u4e00" <= ch <= "\u9fff" for ch in tag) else 3
```

两条单测锁住：中文两字必须命中、英文两字母仍然不许命中（防止修完把原来防的东西放进来）。

> **⭐ 这个 bug 值得记住的三点：**
>
> 1. **"调用没效果"要分三种**：没召回 / 召回了没读 / 读了没用。
>    这次是第一种，但症状和第三种一模一样（都是"加了 skill 也没变好"）。
>    所以 `skill_hits` 和 `skill_loaded` 必须分开记录 —— 只记一个的话这次会误判成"skill 无效"。
> 2. **侥幸通过不算通过**。前 7 个 skill 全绿，但有一部分是"英文 tag 运气好"。
>    测试通过率掩盖了**部分功能永久失效**。
> 3. **修复本身可能有副作用**（见下），所以修完必须重看召回清单，不能只看目标那条。

### Batch AA（2026-11-02 夜，t37 回刷审批 —— 换赛道：多步判断链）

**为什么换赛道**：t35 / t36 连续两题都只剩 **1 个检查点**在区分，
其余条目 base 靠常识全猜对。说明"某公司的参数表"这条路线的结构性缺口快用完了。

这题换的是**结构**，不是内容：不考"填几个数字"，考
**几条规则按固定顺序依次判、先命中的生效**，其中第一条还是**短路**。

#### 题目设计：五步判断链

| 步 | 条件 | 返回 | 直觉会怎么做 |
| --- | --- | --- | --- |
| 0 | 小表（<100 万行）**且**非核心 | `run`，**跳过后续全部检查** | 小表也得走流程、也要查重 |
| 1 | 当日已回刷过（≥1 次） | `reject` | 警告 / 排队 / 等次日 |
| 2 | 窗口 > 30 天 | `queue` 离线队列 | 阈值猜 7 天，或写 `>=` |
| 3 | 有下游在消费 | `wait` 到次日 | 拒绝，或照样跑 |
| 4 | 其余 | `run` | — |

短路那一层是关键：**命中第 0 步就不再执行任何检查**。
放在后面等于没有——只要当日重复或窗口超标就永远走不到它。

#### 结果

| 模式 | 通过 | 每次通过几个检查点 |
| --- | ---: | ---: |
| base | **0 / 3** | **0 / 6**（三次完全相同） |
| skill | **3 / 3** | 6 / 6 |

token 两侧几乎一样（base 23k–28k，skill 18k–25k）——**这题不靠信息量取胜，靠判断顺序**。

#### ⭐ 6 个检查点全部有区分度 —— t33 之后第一次

t35 是 3/4 猜对、t36 是 4/5 猜对，都只剩一个数字。
这题 base **0/6**，六个检查点逐个都能单独抓住它：

```
FAIL 小表直通（跳过后续全部检查）
FAIL 当日已回刷过 → 拒绝
FAIL 窗口边界 30 天（>30 才排队）
FAIL 有下游消费 → 等次日
FAIL 判定顺序：排队优先于等次日
FAIL 核心表不适用直通
```

> **结论：不是"知识更多"，是"结构更复杂"。**
> 让 agent 猜一个数字，它有一半机会；让它同时猜对
> **4 条规则 + 1 个顺序 + 1 个短路**，概率就低了。
> 而且错了能报出**漏了哪一条**，比"全错"更有诊断价值。

#### base 的实现：非常专业，方向全错

```python
MAX_SAME_DAY_BACKFILLS = 2      # 一天最多回刷 2 次（规定是 1）
MAX_WINDOW_DAYS = 30
MAX_ROW_COUNT = 100_000_000     # 自己发明的行数上限
BUSY_SUBSCRIBERS = 1

if window_days > MAX_WINDOW_DAYS or row_count > MAX_ROW_COUNT:  return "reject"
if same_day >= MAX_SAME_DAY_BACKFILLS:                          return "wait"
if subscribers >= BUSY_SUBSCRIBERS:                             return "queue"
if is_core:                                                     return "queue"
return "run"                                                    # 没有直通概念
```

四条判定**方向全反**，但每一条单独看都像正经工程实践：

- "规模超限就直接拒绝" —— 合理，但规定是进离线队列（能跑，只是不在线上跑）
- "今天已经跑过 2 次了，明天再说" —— 合理，但规定是第 2 次就拒绝
- "有下游在消费就排队" —— 合理，但规定是等到次日（排队当晚就会跑，仍然会撞上）
- "核心表一律走队列" —— 合理，但它因此完全没有"直通"这个概念

> 这是 t34 教训的重演，但更强：**不是"猜错一个数"，是"整条链的语义都换了"**。
> 它构造出的是一套**自洽的、在别的公司可能真的成立的**规章制度。

#### 🔴 我又犯了一次同类错误：判卷假阳性

第一版第 5 条检查是「同时"当日已回刷"和"窗口 60 天"→ 应返回 `reject`」，
用来测 `reject` 优先于 `queue`。base **通过了**这条。

原因：base 里"窗口超限就 `reject`"这条错误规则，**恰好也返回 `reject`**。
检查测的是返回值，分不清是"顺序对"还是"规则错但结果碰巧一样"。

→ 这正是 t31 那次的同类错误：**检查点没有区分能力，却显示通过。**

修法：换成 `window=60` + `subscribers=3` → 应返回 `queue`（测 `queue` 优先于 `wait`）。
base 返回 `reject`，现在**六条全 FAIL**；7 个变异也仍然全被拦。

> 一条检查"能拦住变异"和"能区分 base"是**两件事**。
> 前者证明判卷不太松，后者证明这道题在测东西。
> 第一版第 5 条：拦得住变异，但分不出 base —— 属于**看起来严、实际空转**。

### Batch AB（2026-11-02 夜，t38 导出审批 —— 第 10 题，以及一个**动摇全部结论的发现**）

#### 一、第一版设计失败：base 猜对 4 条

第一版规则是"外部一律拒 / 敏感就脱敏 / 行数超限转人工"。
base 三次跑了 0/3，但**每次通过 3–4 个检查点**：

```
PASS  外部出口一律拒绝        ← 安全常识
PASS  含敏感字段 → 脱敏而非拒绝  ← 安全常识
PASS  超过 10 万行 → 转人工     ← 安全常识
PASS  判定顺序：外部优先于脱敏   ← 碰巧
FAIL  本部门内部直通
FAIL  本部门但发往外部 → 仍拒绝
```

只有"本部门直通"这一个真缺口，跟 t35 一个水平。

> **教训：结构复杂 ≠ 有区分度。**
> t37 之所以六条全 FAIL，不是因为"五步链"这个结构，而是因为
> **四条判定方向全反**。t38 第一版把常识套进了复杂结构里，结果结构白搭。
> **结构只负责"让它同时对 6 件事"，内容负责"让它每件都猜错"。缺一不可。**

#### 二、改造：让同一个字段在不同去向下有**相反**的结论

| 步 | 条件 | 返回 | 直觉 |
| --- | --- | --- | --- |
| 0 | 本部门 **且** 内部 | `allow`，跳过后续全部 | 本部门也要查 |
| 1 | **内部** 且 含敏感 | **`deny`** | 脱敏后放行 |
| 2 | **外部** 且 含敏感 | **`mask`** | 外部一律拒 |
| 3 | 行数 > **50 万** | `review` | 阈值猜 10 万 |
| 4 | 其余 | `allow` | — |

第 1、2 步是核心：**同样"含敏感字段"，内部直接拒、对外脱敏放行。**
模型一定会把"敏感字段"当同一个维度统一处理，一旦统一，两条检查点同时失败。
（业务上自洽：部门之间该走接口，导出成文件就脱离权限体系；对外发的是聚合结果，脱敏后本就该给。）

| 加入反例 t32 | 11 | 0.864 | 8.86 |

- 剔除 t35/t36 → 结论不变、均值差略升，说明这两题没在"撑"结论，是在拉低它。
- **加入 t32 → 效应从 0.950 掉到 0.864，方向不变。**
  这条必须报：排除 t32 是**后验筛选**，有影响，但不推翻结论。

#### 三条必须写进结论的局限

1. **base 恒为 0 是设计出来的**：造题时就按"base 会失败"筛，t32 就是因此被排除。
   所以这是**筛选后的样本**，不能推广成"skill 提升一般任务 95 个百分点"。
2. **skill 是为这些题写的**（构造效度）：先造题再补 skill 的顺序是对的，
   但"能补上 skill"本身成了入选条件，盖不住的 t30 就被排除在统计外。
3. **n=10 是配对 t 的下限**，符号检验全同向时 p=0.001 已接近这种设计的极限。

#### 可以对外说 / 不能说

**可以说**：在 10 个"答案不在仓库里"的任务上，无 skill 时 31 次有交付的运行全部失败，
有 skill 时 27/28 通过；**10 次配对全部同向，符号检验 p = 0.001**。

**不能说**：
- ❌ "通过率提升 95 个百分点"（筛选 + 天花板）
- ❌ "t=19 效果极其显著"（该引符号检验）
- ❌ "skill 让 agent 整体变强"（只在这类任务上验证过）

#### 下一步（比再造题更有价值）

1. **随机抽样任务集**（哪怕 5 个），看 base 天然能过多少 —— 这才能估效应量。
2. **留出任务**：用 t27–t37 的 skill 库跑 t38，不给它写新 skill，
   测的是"召回泛化"而不是"知识覆盖"。
3. **验零交付新假设**：沙箱修好后重跑 t34/t35。

### Batch AD（2026-11-07）留出任务 t39 —— 第一次测"skill 能不能迁移"

#### 为什么做这个

前 10 题的共同问题：**每篇 skill 都是题做完才写的** —— 等于开卷考试。
"skill 有效"只能说明"答案放在它能拿到的地方时，它抄得对"，
不能说明 skill 有**可迁移的知识价值**。

所以造 t39（告警静默审批），**不给它写配套 skill**，只要它和现有某篇同构：

| 步 | 条件 | 返回 | 直觉 |
| --- | --- | --- | --- |
| 0 | 单条规则 **且** ≤ 30 分钟 | `apply`，跳过后续 | 静默总得审批 |
| 1 | 范围是**全局** | `reject` | 短时全局可以放 |
| 2 | 覆盖业务高峰 | `review` | 高峰绝不能静默 |
| 3 | > 24 小时 | `schedule` | 太长该人工审 |
| 4 | 其余 | `apply` | — |

和 `backfill-approval-policy` / `export-approval-policy` 同构（复合短路 + 顺序 + 同字段双结论），
业务与全部参数不同。

#### 三组结果

| 组 | 给什么 | 通过 | 每次通过几个检查点 | token |
| --- | --- | ---: | --- | ---: |
| A | 什么都不给 | 0/3 | 2 / 4 / 4 | 20k–29k |
| B | **现有 13 篇库** | 0/3 | 2 / 4 / 4 | 34k–38k |
| C | 专属 skill（held-out 里） | **3/3** | 6 / 6 / 6 | 16k–20k |

召回检查：t39 的 prompt 命中 `backfill-approval-policy`（10.36）+ `pytest-style`（4.78）。
**B 组确实拿到了那篇同构的文档**，token 多花 10–15k 就是证据。

#### ⭐ 核心发现：B 和 A 总分一样，但内部结构变了

| 检查点 | A（无 skill） | B（读了同构 skill） |
| --- | --- | --- |
| 单规则短时直通 | FAIL | **PASS** |
| 31 分钟不再豁免 → 转人工 | PASS | **FAIL** |
| 全局静默 → 拒绝 | PASS | PASS |
| 超 24 小时 → 排期 | PASS | PASS |
| 判定顺序：全局优先于高峰 | PASS | PASS |
| 24 小时边界 | FAIL | FAIL |

看两组的实现就明白了：

**A 组**把直通写在函数**最后一条**（`if scope == 'rule' and minutes <= 30: return "apply"` 在末尾），
前面已经全局拒、高峰 review、超时 schedule —— 永远走不到它。**等于没有。**

**B 组**读了 `backfill-approval-policy`，开头注释写的是：

> 第 0 步  单条规则（scope == 'rule'）且时长 <= 60 分钟  → "apply"
> 顺序理由：短时单规则静默影响面最小，直接放行，不必再走后面的检查

**它把直通挪到了第 0 步，而且复述了"不必再走后面的检查"这条原则。**
这是实实在在的**结构迁移**。

但参数全是猜的：短时阈值 60（规定 30）、长时阈值 240（规定 1440）。
所以它赢了"短路"那一条，输了"31 分钟"那一条，**净变化恰好为零**。

> **结论：skill 能迁移"结构"，不能迁移"参数"。**
>
> 这一条很有用：它解释了为什么前 10 题必须 skill 与任务严格对应 ——
> 不是因为模型笨，而是因为**参数知识根本无法从相邻文档里推出来**。
> 结构能学，数字学不会。

#### 另一件要记的事：A 组的"碰巧通过"

A 组 4/6 里有两条是**碰巧**：
- "31 分钟 → 转人工"：它先判高峰，31 分钟撞上高峰 → review，恰好等于期望值；
- "顺序"：它把全局判在高峰前面，恰好对。

这就是 t35 那条教训的现场版：**看 base 通过几条之前，先看它为什么通过。**

### Batch AE（2026-11-09）随机抽样基线 —— 主结论缺的那块「分母」

#### 一、要回答的质疑

> 你那 10 个任务 base 全是 0，**是你筛出来的**。
> 所以「skill 把通过率从 0 提到 27/28」只说明你筛得准，不说明 skill 有用。

这是主结论唯一还没堵上的洞。补法：拿一批**没有按「base 会失败」筛过**的任务，
测 base 的天然通过率。

#### 二、抽样是预注册的（先写规则，再看结果）

- 抽样框：12 个任务（`eval/SAMPLED.md`），全部是**和 t27–t39 同形**的小模块任务：
  单模块 + 3–6 条行为 + 既有测试 + 要改文件。
- 唯一差别：**规格在需求里给全，不需要任何仓库外知识**。
- 种子 `20261109`，`random.sample(frame, 5)` → **s03 / s01 / s08 / s05 / s12**。
- 判定规则先写死（含「若 base 也大面积失败 → 主结论有混杂，要重审」）。
- 抽中即锁定：不换题、不改难度、不因为「base 过了」撤题。

> 为什么不抽「随机日常任务」（hello world 级别）：那样 base 当然全过，
> 但这说明不了任何事 —— **难度变了，不是「缺口」变了**。
> 要让对照有意义，必须只动一个变量：规格在不在仓库里。

#### 三、结果

| 任务 | 规格内容 | base（3 次） | skill（3 次） |
| --- | --- | ---: | ---: |
| s01 日期按自然月切分 | 闰年/单日/跨年/非法格式全给 | 3/3 | 3/3 |
| s03 金额按权重分摊 | 最大余数法 + 平局规则全给 | 3/3 | 3/3 |
| s05 版本号比较 | 补零/预发布顺序/非法输入全给 | 3/3 | 3/3 |
| s08 LRU 缓存 | 容量/刷新/淘汰顺序全给 | 3/3 | 3/3 |
| s12 模板渲染 | 空格容错/KeyError/未闭合全给 | 3/3 | 3/3 |
| **合计** | | **15 / 15** | **15 / 15** |

**base 一次都没失败。** 15 次全部通过，且都是 5–10 次工具调用内完成。

#### 四、这条结果的价值：它是「阴性对照」，不是「白做了」

| | 规格在仓库里（抽样 5 题） | 规格不在仓库里（t27–t38，10 题） |
| --- | --- | --- |
| base | **15 / 15** | **0 / 31**（有交付的） |
| skill | 15 / 15 | 27 / 28 |

同一个 agent、同一套工具、同一种任务形状（单模块 + 多检查点判卷），
**唯一变量是「规格在不在仓库里」，通过率从 100% 掉到 0%。**

> 这直接堵掉了两个质疑：
> 1. **「base=0 是因为你的任务太难/脚手架坏了」** —— 同一个脚手架，同形任务 15/15 全过。
> 2. **「base=0 是因为模型能力不足」** —— 它在同类任务上写对了浮点分摊的平局规则、
>    LRU 的淘汰顺序、版本号的预发布顺序，这些都不是简单活。

**所以 skill 的价值有明确的适用边界**：它不是「让 agent 变强」，
而是**补上「规格不在仓库里」这一种缺失**。

#### 五、代价：在这类任务上 skill 是纯开销

| 任务 | base token | skill token | 差 |
| --- | ---: | ---: | ---: |
| s01 | 17,234 | 25,305 | +47% |
| s03 | 15,019 | 18,968 | +26% |
| s05 | 16,528 | 39,104 | +137% |
| s08 | 17,569 | 16,640 | −5% |
| s12 | 23,804 | 37,656 | +58% |

均值差 **+9,504（+52%）**，t=2.33，df=4，**未达显著**（临界 2.776）；
符号检验 4/5 同向，双尾 p=0.375。

⚠️ **而且这个均值被一个离群值撑起来了**：s05 有 1 次跑出 82k token（15 次调用），
把 s05 的均值从 17.6k 抬到 39k。剔除那一次，s05 的差值是 **+1,055**，全组均值降到约 +4.2k。

> 按纪律：**只能写「成本方向为正、幅度无法确定」，不能引用 +52% 这个数。**
> 这是第 N 次同类坑（压缩 22%、A 组 token 更贵、配对 t=19）——
> 先看均值差，再看 sd。sd 是 9,104，比均值还大。

#### 六、🔴 顺带把「绝对分数下限」这笔债坐实了

5 个抽样任务的召回（它们根本不需要任何外部知识）：

```
s01 -> pytest-style 6.00
s03 -> pytest-style 7.04
s05 -> pytest-style 6.00
s08 -> pytest-style 7.56, rates-api 4.55
s12 -> pytest-style 6.40, messaging-contract 2.95
```

**5/5 全部被塞了不相关文档。** `rates-api`（汇率 API 契约）和 LRU 缓存毫无关系，
`messaging-contract`（MQ 契约）和模板渲染也毫无关系 —— 纯粹是「测试」「字段」这类词撞上的。

这正是待办里那条「`retrieve()` 需要一个绝对分数下限」的现场证据：
现在只有 `min_score=1.5` + `rel=0.3` 的相对过滤，低分项只要没有更高分项压着就会进来。

**判断**：这几个分数（2.95–7.56）和真正的命中（10.36–23.09）之间**有一个空档**，
但 t39 那个真命中只有 10.36，所以阈值不能拍脑袋定 —— 需要看完全部任务的分数分布再定。
（下一步做，不在本轮改。）

#### 七、结论该怎么改口径

之前 README 写：**base 0/31 → skill 27/28，「skill 是唯一能改变对错的机制」**。
这句仍然成立，但要加一句限定：

> 这个机制只对「规格不在仓库里」的任务有效。
> 在规格给全的同形任务上（5 题，base 15/15），它的增益是 0，成本方向为正。
>
> 所以不能写成「接入知识库让 agent 整体提升」，只能写
> **「补齐外部规格这类缺失，能把通过率从 0 提到 27/28；代价是在不需要它的任务上多花 token」**。

效应量的诚实表述：

> skill 的收益 ≈ **「规格缺失」在真实任务里的占比 × 1.0**。
> 我测的是「缺失时能救回多少」（≈100%），**没测「缺失发生的频率」** ——
> 这需要真实工单分布，我没有，也不打算编。

### Batch AF（2026-11-09）修 `retrieve()` 的两道闸门 —— 抽样实验的代价其实是个 bug

#### 触发：Batch AE 里 5/5 抽样任务都被塞了不相关文档

```
s01 -> pytest-style 6.00            s08 -> pytest-style 7.56, rates-api 4.55
s03 -> pytest-style 7.04            s12 -> pytest-style 6.40, messaging-contract 2.95
s05 -> pytest-style 6.00
```

查明细才发现噪声有两个**不同**的成因：

| 成因 | 证据 | 影响面 |
| --- | --- | --- |
| **通用词冒充证据** | `pytest-style` 靠 `pytest` + `test` 命中 | **20 个任务**（几乎每个 prompt 都写"跑一遍 pytest 确认"） |
| **单一宽泛 tag 分数低但过线** | t27 误召 `retry-budget` 9.2、t38 误召 `backfill` 9.6、s08 误召 `rates-api` 4.5（靠 tag `cache`） | 4–5 个任务 |

第一条尤其讽刺：`_tag_hits` 的注释里写着"用 tag 而不是 BM25，就是因为通用词会把一切都连接起来"，
结果**在 tag 这一层又犯了一次同样的错**。`pytest` 就是这么个通用词。

#### 修法：两道闸门（不是调一个数）

1. **`GENERIC_TAGS` 白名单外**：`test/tests/testing/pytest/unittest/code/file/function/
   测试/代码/文件/函数/字段/数据` 这些词**可以陪跑、不能单独构成召回**。
   判据：它们在任何工程任务里都出现，命中它等于没有信息。
2. **`min_abs = 10.0` 绝对分数下限**（原来只有 `min_score=1.0` + `rel=0.35` 的相对过滤，
   靠"有更高分项压着"才偶然挡住低分项）。

阈值 10.0 的来历（**不是拍脑袋，但余量很薄**）：

```
噪声 2.0–9.6   ← t27 retry-budget 9.2、t38 backfill 9.6
     ↑ 10.0
边界 10.4      ← t39 只靠一个 tag "审批"
真命中 13.3–29.8
```

10.0 卡在 9.6 和 10.4 之间，**两边各留 0.4 分**。

> ⚠️ 这 0.8 分的缝说明了分数的极限：它**分不清"结构相似"和"词撞上了"**。
> t39 的 10.4 和 t38 的 9.6 都同构（都是审批流），一个是真有用、一个是纯开销，
> 靠 0.4 分的差距区分它们属于运气。要彻底解决得换判据（tag 语义分层），不是调阈值。

#### 效果

**召回清单从"24/44 个 prompt 有召回"变成"12/44"，且这 12 个每一个都对着正确的那一篇：**

```
t27 rates-api 19.0 | t28 messaging-contract 29.8 | t29 logging-standard 18.2
t31 retry-budget 15.4 | t32 report-export-encoding 13.3 | t33 sla-timeout-policy 22.2
t34 canary-gate-policy 26.3 | t35 tracking-event-policy 26.4 | t36 rate-limit-policy 17.0
t37 backfill-approval-policy 23.0 | t38 export-approval-policy 21.8 | t39 backfill 10.4
```

**抽样 5 题全部零召回。** 其余 32 个 prompt（含 t01–t26）也全部零召回。

#### ⭐ 重跑抽样 skill 组：**代价消失了**

| 任务 | base | 修复前 skill | 修复后 skill | 前−基 | 后−基 |
| --- | ---: | ---: | ---: | ---: | ---: |
| s01 | 17,234 | 25,305 | 15,713 | +8,071 | **−1,521** |
| s03 | 15,019 | 18,968 | 22,769 | +3,949 | +7,750 |
| s05 | 16,528 | 39,104 | 17,284 | +22,576 | **+756** |
| s08 | 17,569 | 16,640 | 15,854 | −930 | **−1,715** |
| s12 | 23,804 | 37,656 | 17,255 | +13,852 | **−6,550** |
| **均值** | | **+9,504**（sd 9,104） | **−256**（sd 5,207） | | |
| 注入次数 | | **15/15** | **0/15** | | |

> **原来那个 +9,504 不是"skill 的固有成本"，是"注入了不相干文档"的 bug。**
> 修完以后在不需要 skill 的任务上，它与 base 无差别（−256，且 sd 减半）。
>
> 这条修正很重要：之前 README 写"成本方向为正"，那是**在 bug 存在时测的**。
> 现在可以说：**在规格给全的任务上，修复后的路由是零成本的**。

#### 判定：修复本身有没有副作用

- 12 个真任务的**首位召回完全没变**（分数也没变），所以通过率不该受影响；
- 抽样做的抽查：t27、t38 各跑 1 次 skill → **2/2 通过**（烟测，不是复验 3/3 的记录）；
- 全量单测 **88 passed**（新增 4 条路由机制 + 18 条真实语料快照）。

#### ⚠️ 一个必须承认的脆弱点：绝对分数不可移植

改单测时撞到：把同一个判定搬到"只有 1–2 篇 skill"的迷你语料里，
真命中也只有 5–6 分 —— 因为 `score` 里 `0.2 × BM25` 会随语料规模剧烈变化。

所以做了分层：
- `tests/test_skill_router.py`：只测打分机制，显式传 `min_abs=0`；
- `tests/test_recall_snapshot.py`：拿**真实 13 篇库**锁"哪些该召回、哪些不该"
  （含一条"整体召回率不能超过 12/44"，防止"全都召回"也能通过）。

> **结论：`min_abs=10.0` 是"这个语料 + 这批 prompt"上的值，不是通用常数。**
> 技能库翻倍后必须重标定，否则会变成静默漏召。这条写进 README 的已知限制。
